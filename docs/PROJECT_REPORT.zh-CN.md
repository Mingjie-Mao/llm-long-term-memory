## 一、设计目标与边界

### 要解决的问题

一个大模型应用跨会话地"记得用户"，通常有三条路：每次把整段历史塞进上下文、对历史做向量检索、
或者把历史抽成结构化事实再检索。第一条准确但昂贵，第二条便宜但召回的是"最像的段落"而不是
"当前成立的事实"，第三条要面对一个真问题——**抽取本身会丢东西**。

这个项目走第三条，并且把"丢了多少、丢在哪一层"当成主要研究对象，而不是当成实现细节。

### 只做长期记忆

记忆常见的三分法是工作记忆（任务中间状态：查过什么、调了什么工具、走到第几步）、
短期记忆（当前这轮对话）、长期记忆（跨会话的偏好、事实、事件）。

**这个项目只有第三种。**

| | 本项目的处理 | 状态 |
|---|---|---|
| 工作记忆 | 没有。代码里不存在任务状态、工具调用记录、步骤指针 | 整层缺失 |
| 短期记忆 | 不建模。当前这一轮由调用方自己放进提示词 | 不在范围内 |
| 长期记忆 | 全部工作在这里：抽取、存储、时间线、检索、装配 | 已实现并测量 |

一个需要澄清的混淆：**结构化记忆库不等于工作记忆**。它存的是"用户是谁、说过什么、什么时候变的"，
不是"这个任务干到哪了"。两者的生命周期正好相反——工作记忆任务结束就该丢掉，长期记忆任务结束
才刚开始有用。所以工作记忆不该建在这套索引上，它需要的是可丢弃的、按任务划界的短生命周期存储。

长期记忆内部再分两层标签：五种类型（`semantic`、`episodic`、`preference`、`procedural`、
`profile`）和七种范围（`profile`、`preference`、`plan`、`recommendation`、`commitment`、
`event`、`shared_context`）。范围由抽取器判定，**没有经过人工核验**，所以它可以用来过滤，
不能用来下结论。

### 边界

- **这是原型，不是产品。** 写入在单进程内串行、锁跨模型调用持有、SQLite 与向量索引是两个各自
  落盘的文件。多进程并发与跨资源原子性没有闭环，而且两者要的是换一套存储，不是打补丁。
- **不做 SOTA 声明。** 对照是自己的基线（整段历史、朴素检索），不是排行榜。
- **一个基准，用尽即止。** LongMemEval-S 的 500 道题已经切成五个互不相交的集合并全部用完，
  所以 v4 至今没有终测。这是已声明的阻塞条件，不是脚注。

选 LongMemEval 而不是更常被引用的 LoCoMo，理由是金标与评分器的可靠性：LoCoMo 的标注问题在公开
讨论里被反复指出，而这个项目没有标注预算去逐题复核一份自己不信的金标。这个选择也有代价——
LongMemEval 的评分细则**不用自己的话点名所需事实**，所以第四章里那个"事实级覆盖"的诊断层在这份
数据上做不出来。选基准就是选能测什么和不能测什么。

## 二、核心设计

### 1. 两阶段记忆抽取

抽取器（`TwoStageExtractor`）把一次抽取拆成两步：阶段 A 只要句子，阶段 B 才结构化。

| 字段 | 来自 | 说明 |
|---|---|---|
| `content` | 阶段 A | 一句自足的话，代词已解析，数字、日期、名称逐字保留 |
| `source_role` | 阶段 A | 谁说的：user / assistant / system |
| `subject` | 阶段 A | 这条事实是关于谁的——不是说话的人 |
| `scope` | 阶段 A | 七种范围之一 |
| `temporal_key` | 阶段 B | 这条事实占据的属性槽位 |
| `update_op` | 阶段 B | `coexists` / `replaces` / `none` |
| `object` | 阶段 B | 槽位上的值 |
| 类型、实体、重要性、事件时间 | 规则 | 模型没有优势的字段不花调用 |

**拆两阶段的理由是实测的。** 单阶段一次要模型输出九个字段，而**每条事实的输出成本压制了它愿意
写下多少条**。拆开之后阶段 A 只写句子，会话下标从"模型要填对的一个字段"变成结构性的，
`dropped_bad_index` 这一类失败直接消失。

代价是一批非空事实通常要两次请求（阶段 A + 阶段 B），判重可能再加若干次。阶段 A 没抽到事实时
跳过阶段 B。

**助手轮次也抽。** 用户说的和模型答的都进抽取，因为"助手推荐过什么"经常就是后来被问的东西。
代价是记忆里有相当比例以"助手推荐了……"开头，这在计数类问题上会变成噪声。

### 2. 结构化记忆与原文双层保存

抽取出的结构化事实和**逐字保存的原始轮次**同时入库，各自承担不同职责：

| | 职责 |
|---|---|
| 结构化记忆 | 压缩、排序、状态更新。它是检索的主路径 |
| 原始轮次 | 恢复被抽取丢掉的链接、数字、措辞。它是回退的材料 |

原文不是只能写入无法查询的日志：`turns_fts` 让它可以被关键词检索到。这一点很重要——**抽取是
有损的，而这份损失的兜底不是"抽得更好"，是"原文还在"**。

存储形态是刻意保守的：SQLite 存源数据、状态、词法索引和辅助关系，向量是一个 `N × 384` 的
归一化矩阵单独落盘，行号到记忆 ID 的对应关系由应用维护。不用外部向量数据库，也不用 ANN 索引——
在这个量级上精确检索够快，而一个近似索引会在诊断阶段引入一个说不清的变量。

**这里没有分层压缩。** 没有"三年前压成一段、一个月前浓缩成一条"。设计不同：**抽取本身就是压缩**，
在写入时做一次；原始轮次逐字留着，不删。

### 3. 时间状态与冲突更新

这是项目做得最好的一层，实现在时间状态解析器（`TemporalResolver`）。

**时间线是重建的，不是打补丁的。** 直觉做法是拿新事实和当前头部比较、让输家退位；但只要摄取顺序
和事件顺序不一致就会坏掉，而在批量管线上这是立刻发生的：一月的事实在八月之后到达，会让一月重新
变成"当前"。所以解析器读取某个键下的**全部**记忆（包括已退位的），按事件时间排序，重新写出这条
时间线蕴含的全部区间。结果是**幂等、与到达顺序无关**。

**重述不算变化。** 三月说"我用 PyTorch"，八月又说一次，不移动任何东西：连续的同值提及折叠成一个
区间，归属于**最早**的那次，所以"你什么时候换的"答的是三月。

**这一层不调模型。** 按事件时间排序是对抽取器已经附上的数据做算术。在这条路径上放一次模型调用，
等于每条记忆收一次费去做一个不需要模型的决定。没有日期的事实被报告出来、原样留着，不猜。

**旧值不会被删掉。** 这套设计写的是有效区间（`valid_from` / `valid_to`），不是删除：旧值仍在
库里，只是默认不进上下文。要查历史有两条路——按时间点回放，或者直接列出这个键的完整变化史。

是否关闭前一条由**下一条事实**的更新操作决定，不是"同键出现过一次替换"就把所有事实排成互斥链：
`coexists` 允许并存，`removes` 记录为结束操作。

去重是另一条线：新记忆与近邻比对，由模型裁定 DUPLICATE / UPDATE / DISTINCT。0.92 只是近邻
**候选**阈值，不是"到阈值就丢"。在一次 22 段密集对话的摄取里实测，裁定请求约为抽取请求的
0.7–1.1 倍，随库密度上升。

### 4. 条件原文恢复

答题器第一次回答返回的不是自然语言，而是一个结构化判定：

| 判定 | 行为 |
|---|---|
| `answer` | 直接返回，不搜原文，不做第二次回答 |
| `need_source` | 同时考虑选中记忆的来源和原文 BM25 排名，选 source-local 或 archive-wide |
| `no_evidence` | 仍然搜原文，但不带选中记忆的来源锚点，即 archive-wide |

恢复器（`RawFallback`）**先搜索并排名原文，再截断**。有本地出处、且最佳 BM25 命中落在这些出处
里时优先返回本地轮次；没有 BM25 命中但有本地轮次时也用本地轮次；否则用 archive-wide 命中。
**只有真的找到原文才调用第二次回答器**，没找到就保留判定里的文本或者答不知道。

默认上限：最多 3 个轮次、2,400 个原文字符。

这条路径是有效的：`test100` 上回退触发 **35.0%**，其中 **18.0%** 的结果是回退之后才对的；
`dev50` 上同一套系统关回退 56.0%、开回退 **72.0%**。

**但它有一个结构性的盲区**：回退只在答题器**自己察觉**到缺东西时才触发。它没察觉、直接用一条
丢了数字的记忆作答的情况，回退救不了。这正是抽取保真度是最弱一环的原因，也是第四章的主题。

另一条防线是弃答：答题器被明确要求在没有事实支撑时说不知道而不是猜。`dev50` 上弃答类两个记忆臂
都是 100%。

## 三、关键实验结果

完整口径、对照臂定义和证据文件索引在[评测说明](EVALUATION.md)，这里只讲结论。

### 1. v2 最终结果：上下文效率是最清楚的成果

`test100`，100 题，每臂一次，同一个评分器：

| 方法 | 正确率 | 中位回答上下文 token |
|---|---:|---:|
| v2 记忆＋条件回退 | 72% | **574** |
| 整段历史 | **86%** | 109,059 |
| naive RAG | 65% | 12,763 |

**要诚实读这三行。**

- v2 比朴素检索高 7 个百分点，但配对检验 **p = 0.3368**。这不足以证明稳定优势，只能说没有
  测出差别。
- 整段历史比 v2 高 14 个百分点，**p = 0.0043**。这是一个真实的劣势。
- 真正站得住的成果是**上下文**：574 对 109,059，两个数量级。即使正确率输 14 个点，"用 0.5%
  的上下文拿到 84% 的准确率"仍然是一个有意义的工程结论。

上下文比值的口径要说清：记忆/RAG 是字符估算，整段历史用的是 provider 输入 token，所以约 190 倍
是**近似上下文比值**，不是账单承诺。

### 2. 时间推理与状态更新：相对基线优势最明确的地方

同一次终测的题型切片：`knowledge-update` **75.0%**、`temporal-reasoning` **74.1%**。

作为对照，`dev50` 上整段历史基线的时序题只有 **23.1%**、朴素检索 **46.2%**。

这个差距是设计带来的，而且机制清楚：整段历史把同一个属性的新旧值一起给模型，模型要自己判断
哪个是当前值；本项目在写入时就把时间线算好了，默认只把当前区间送进上下文。**把一个确定性问题
用算术解决，而不是每次让模型重判一遍。**

### 3. 抽取保真度：瓶颈是批大小，不是抽取器设计

这是最新、也是最有价值的一个结果。

长期挂在这个项目头上的数字是"抽取保真度只有 36.6%"，并且一直被当成抽取器设计的问题——为此改过
三次提示词、加过工作示例、试过带证据引用的抽取器。

**2026-09-16 的实验说明它主要是一个操作点的问题。** 同一批 60 个留出会话、同一套提示词、同一个
模型、同一把尺子，只改"每次请求塞几个会话"：

| 每请求会话数 | 整体保真度 | 记忆/会话 |
|---:|---:|---:|
| 15（出厂配置） | **37.3%** | 1.53 |
| **8** | **64.9%** | 3.72 |
| 5 | 66.4% | 4.97 |
| 3 | 70.9% | 6.38 |
| 1 | 78.4% | 13.10 |

批 15 的 37.3% 几乎精确复现了此前记录的 36.6%，所以**尺子没有漂移**——那个数字是可靠的，
但它是**批大小 15 这个操作点**的属性。

**15 → 8 是目前找到的性价比最高的改进点。** 134 条具体信息在每个臂里都问过一次，可以做配对
精确 McNemar：15 → 8 是 **+41 / −4，p = 9.3e-09**；而紧接着的 8 → 5 是 **+8 / −6，p = 0.79**，
在同样 134 个条目上和噪声没有区别。

所以 8 不是从折线的"视觉拐点"挑出来的，**是从证据用尽的地方挑出来的**。从曲线形状挑工作点
等于从噪声里挑。

机制也清楚：十五个会话共享一个提示词时，模型的输出预算被摊薄到每会话一条半记忆，而被挤掉的
正是规格——时长从 85.7% 掉到 35.7%，专名从 77.4% 掉到 34.0%。留下的是每个会话的主旨句，
而问题问的恰恰是主旨句里被省掉的那些数字。

代价：`dev100` 重建在批 8 下约 4–6 个配额日，批 15 是 2.8 个（实测）。候选配置
`configs/v2b-batch8.yaml` 已写好，与 v2 逐字段只差这一个参数（有测试校验），**尚未按规模跑过**。
它改变摄取指纹，所以现有的库只能重建不能续跑；已归档的结论不受影响，它们记录的是各自操作点上的
真实读数。

**一个附带的负结果：要求逐字引用原文不能提高保真度。** 带证据引用的抽取器在同样每请求一个会话
的条件下拿到 64.2%，比对照低 14 个点，配对 **−27 / +8，p = 0.0019**。原因是要求引用之后写下来
的记忆只剩三分之一。**在这份语料上，可追溯性和召回是对立的，不是互补的。** 它作为可审计性手段
仍然成立——每条记忆能指向原文是一个独立的价值——但那是另一个目标，不该记在保真度账上。

### 4. 检索权重：每加一路都更差

检索器实现了五路信号：语义相似度、BM25、时间衰减、重要性、实体重合。**v2 只开语义，其余四路
权重全是 0。**

这不是没做，是**做了、测了、否掉了**（`train150`，150 题，零调用）：

| 权重配置 | Top-3 命中 | 相对基线 |
|---|---:|---:|
| 仅语义 1.0（出厂配置） | **95.3%** | — |
| + 时间衰减 0.3 | 95.3% | 逐位相同 |
| + 重要性 0.3 | 90.0% | −5.3 |
| + BM25 0.5 | 89.3% | −6.0 |
| 五路全开 | 87.3% | −8.0 |
| + 实体 0.5 | 78.0% | **−17.3** |

**时间衰减那一行不是打平，是死信号。** 半衰期配的是 30 天，而语料里最新的记忆已经 932 天；
18,519 条记忆里 `S_recency > 0.01` 的有 **0 条**。这是配置缺陷不是信号缺陷——在一份全是三年前
对话的语料上，任何 30 天半衰期都会把所有东西压成零。

所以关于"好的检索应该找到当下最该想起来的，而不是最像的"：**这个目标是对的，但本项目目前不是
靠加权实现的。** 它靠两件事——语义召回，加上时间层把已经被推翻的事实排除在上下文之外。加权那条
路在这份数据上实测无效；在一份有新鲜时间跨度的语料上是否成立，**未测**。

BM25 并没有被浪费：它是**原文回退**的检索器。所以"专有名词会被 embedding 稀释掉"这个担心，
落在回退路径上而不是主检索上。

## 四、失败发生在哪里

一个答案要对，必须连续通过五层。每一层都会丢东西，而**下面每一层都继承上面的损失**。

```
原文 → 抽取 → 检索 → 上下文组装 → 回答利用
```

| 层 | 丢什么 | 实测 |
|---|---|---|
| 原文 | 不丢。逐字入库 | — |
| **抽取** | 用户说出口的具体信息没被写下来 | 批 15 下丢掉 **62.7%** 的具体信息；`dev50` 上 14 个失败里 **10 个**首要原因在这里 |
| 检索 | 记忆在库里但没被召回 | 失败分类里检索失败 **0–6%** |
| 上下文组装 | 召回了但没进最终提示词 | 预算上限；v2 的 574 token 远低于上限，这一层当前不是瓶颈 |
| 回答利用 | 证据在上下文里但没被用对 | 有源却弃权 **44–50%** |

每个错答只分配一个首要原因（E1 抽取丢失 / E2 检索未召回 / E3 时间解析错 / E4 组装丢失 /
E5 回答推理失败 / E6 评分器判错），分类表和工具在[评测说明](EVALUATION.md)。

### 为什么"命中来源会话"不等于"关键事实已进入上下文"

这是整套诊断里最容易被读错的一条，值得单独说。

v2 在 **94%** 的题上选中了至少一个来源会话，但正确率是 **72%**。另一处更极端：某次比较里来源
召回是 **98.3%**，正确率 **55.0%**。

差距的来源是**这两个指标测的不是同一件事**：

- "来源会话召回"只说明——被选中的某条记忆，它的 `source_session_id` 指向一个被标注为答案来源的
  会话。
- 它**不说明**这条记忆里含有支撑答案的那个事实。

一个会话可能有几十轮，抽取从中写出一两条记忆。**这一两条完全可以来自正确的会话，却恰好丢掉了
问题问的那个数字。** 检索把它召回了，指标记为命中，而上下文里其实没有答案。

v2 的 28 个错答分解正说明这一点：3 个没找到来源会话，14 个在原文回退后仍错，**11 个已有来源
上下文仍错**。也就是说，四分之三的错答发生在"来源已经找到"之后。

所以来源召回是一个**必要不充分**的指标。它适合用来排除检索问题，不适合用来声称证据完整。
更强的指标需要基准自己用文字点名所需事实，LongMemEval 没有这个，所以本项目只能零成本地报出
更严的一版——**每一个**标注来源会话都进了上下文——而不能报事实级覆盖。

### 一个在这一层之外的缺陷：去重曾经不按命名空间隔离

去重器的近邻搜索在共享索引上进行，**没有 `user_id` 条件**，而检索是有的。

在 `test100` 上零成本采样 1,500 条候选：阈值以上的近邻里**同命名空间 3 个，跨命名空间 42 个**，
还有 2 条候选的整个近邻窗口全是外来记忆。所以这不是边角情况，是常态。

每一个跨命名空间的对，都是去重器若两条同在库里就会去裁决的对；一个 DUPLICATE 判定会从一段
从未包含那条"重复"的对话里删掉一个事实。而被外来记忆占满的窗口，同时也挤掉了去重本来要抓的
同命名空间重复。

**2026-09-16 已修。** 近邻过滤放在检索之后，所以 `limit` 仍然是"看几条索引命中"，这个改动只会
**缩小**窗口——它减少裁定调用，不可能增加一次 DUPLICATE 丢弃。

修复有一半不在去重代码里。改了比较范围而不记录它，就会允许旧策略下建的库被新策略续跑，留下一个
分不出来源的混合库——这正是摄取指纹存在的理由。所以指纹里新增了 `dedup_scope` 字段，并且是从
去重器对象上读的而不是写死的。代价是真实的并且被接受了：**此前建的每一个库都会拒绝续跑**，
要么 `--fresh` 重建，要么换一个库名。已归档的结论不受影响，它们记录的是各自策略下的真实读数。

## 五、当前局限

### 1. 抽取仍然会丢关键事实

即使把批大小降到 1，保真度也只有 78.4%，仍有五分之一的具体信息没被写下来。而当前出厂配置是
37.3%。这是整条链路最弱的一环，也是失败分类里最大的一类。

已经建好的兜底是原文回退，但它只在答题器自己察觉到缺东西时才触发——**它没察觉就救不了**。

### 2. 关键事实没有明确优先级

救命信息和随口一句走完全相同的路径。重要性由规则给，不由模型判。现在没有任何机制让"过敏"
这类事实获得更高的写入保证或更强的抗淘汰能力。

相关的还有一个具体缺陷：事件时间取的是**会话**的日期而不是事实自身的时间，所以同一段对话里的
记忆共享一个时间戳（4,714 个会话只有 3,776 个不同的时间值）。解析不出来时应当留空而不是填
会话日期。

### 3. 长期增长后的衰减与淘汰没有充分验证

衰减、访问强化、容量淘汰都实现了，**默认全部关闭**，而且从未在一份会持续增长的语料上标定过。
已知的情况是：时间衰减在当前语料上是死信号（半衰期配置问题）；淘汰在每命名空间 400 条时免费，
降到 200 条要付 8.6 个点。

这意味着"库越存越多会不会变成垃圾场"这个问题，**本项目目前没有实测答案**。现状是记忆没有时间
上限也没有容量上限，只有显式删除和时间线退位两种消失方式。

### 4. 没有独立的工作记忆层

这一层完全缺失。如果目标是"记住用户"，现有划分够用；如果目标是做 agent，工作记忆是缺的一整层，
而且它不该建在这套索引上。

另外还有两处已知的工程边界：跨进程并发没有保障（进程内的锁在多进程部署下会被绕过），
删除不跨资源原子（SQLite 行先删、向量后删，中途崩溃留下孤立向量而不是可被检索到的幽灵记忆——
方向是安全的，但不是原子的）。

## 六、下一步

按"能不能用现有证据说清代价和收益"排序。

### 1. 提高写入保真度

**第一件事是把每请求会话数从 15 改成 8。** 代价和收益都已经测出来了：2–3 个配额日换 27.6 个点，
候选配置已写好并有测试校验。没有立刻执行是因为它改变摄取指纹、现有的库只能重建，而重建不改变
任何已归档的结论。

第二件是把事件时间和观测时间拆开。这是零调用的改动，依据是上面那个 4,714 / 3,776 的数字。

第三件是把零调用的覆盖检查接进摄取：抽完之后用正则比对原文里的具体信息，只在检出遗漏时才花
一次修复调用。这个函数已经实现，没有接线。

**明确不做的是继续改抽取 schema。** 带证据引用的抽取器已经证伪了"更严的结构能提高保真度"这个
方向——它把产量压到三分之一，净效果是负的。

### 2. 完成证据分层诊断

当前能零成本报出的只有"至少一个来源会话进了上下文"和"每一个来源会话都进了上下文"两层。
第三层——**问题需要的那个事实是否进了上下文**——需要基准自己用文字点名所需事实。

这一层没做完，第四章里那个 94% 对 72% 的差距就只能定性描述，不能定量归因。补上它的路径是明确的：
需要一份带事实级评分细则的数据，而不是更多的分析。

### 3. 在更长、更密集的历史上验证检索与遗忘

当前所有检索和遗忘结论都建立在一份**全是三年前对话**的语料上。这份语料的两个性质直接决定了两个
结论：时间衰减是死信号（因为没有新鲜记忆），淘汰在 400 条时免费（因为库不够大）。

**这两个结论都不能推广。** 要验证的是同一套机制在一份有真实时间跨度、且会持续增长的历史上会
怎样：时间衰减会不会变成有效信号，淘汰的免费阈值会落在哪里，去重的跨命名空间泄漏在库变大之后
是变严重还是被稀释。

这需要新数据而不是新代码，也需要它自己的预注册——它是一个新问题，不是现有指标的一次重跑。

### 明确不做

写下来是为了让"没做"是一个决定，而不是一个遗漏。

- **不在这套索引上加工作记忆层。** 它的生命周期、写入频率和检索方式都与长期记忆相反。真要做
  agent 的时候独立做，接口是任务结束时把结论写进 `POST /v1/messages`。
- **不为了单写入者和双资源问题换存储。** Postgres + pgvector 能一次解决这两件事，但那是重写
  不是修补，属于"原型对产品"的分界。这个项目当前的目标不在那一侧。
- **不再找一个能赢过整段历史的候选。** v2 在冻结终测上输 14 个点、p = 0.0043，而实测的噪声底是
  同配置跑两遍、142 条探针翻转 38 条。在这个信噪比下继续找候选，期望值是负的。真正有价值的是
  把上下文效率那条结论守住，而不是去追一个用两个数量级的上下文换来的准确率。
