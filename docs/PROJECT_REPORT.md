# 项目报告

llm-long-term-memory 从历史对话提取用户事实，记录变更，并为后续问题找回相关证据。
实现细节见[架构](ARCHITECTURE.md)，实验协议与全部结果见[评测](EVALUATION.md)。

## 设计

整段历史准确，但每次回答都要重新处理大量旧内容；按会话做 RAG 便宜，却不容易分清新旧事实。
本项目把这件事放到写入侧：

```text
对话 → 抽取事实和出处 → 去重 → 重建时间状态 → SQLite＋向量索引
                                               ↓
问题 → 检索当前或历史事实 → 必要时读取原始轮次 → 回答
```

每条记忆有主体、属性、值、来源和状态。替换关闭旧值的有效区间，不删除旧值；终止不伪造一个
“新值”，并存事实也不强制互斥。时间线支持乱序写入后重建，`as_of(t)` 可查历史状态。
会话时间与事实时间分开保存；近似相对时间保留原表达和精度，不拿估计日决定替换顺序。

抽取是有损压缩，所以原始轮次也留在库里。记忆负责筛选和状态，原文负责精确数字、日期与措辞。
默认排序以语义相似度为主；没有证据表明增加重排或换向量库能修复当前主要失败。

## 已测结果

冻结 v2 在 100 道 LongMemEval-S 终测题上，每臂运行一次：

| 方法 | 答对 | 回答＋评分 token |
|---|---:|---:|
| 记忆＋条件原文回退 | 72/100 | 159,458 |
| naive RAG | 65/100 | 1,352,847 |
| 整段历史 | 86/100 | 10,932,294 |

v2 对 naive RAG 多答对 7 题，配对精确检验 p=0.3368，不能证明稳定优势；整段历史
多答对 14 题，p=0.0043。token 用量不含共用的抽取阶段，不能读成系统总成本。
[终测汇总](../results/final/test100-aggregate.md)与[冻结配置](../results/frozen/v2-final/freeze.json)
记录了题集、模型、提示词和用量。终测只跑一次，没有重复运行方差。

写入侧发现了可复现的批次效应：同一批 60 会话只把每请求会话数从 15 改为 8，具体信息召回
从 37.3% 升到 64.9%（41 项得、4 项失，p=9.3e-09）。但另一批 60 会话的 batch 8 是
44.8%，780 会话库是 47.5%；64.9% 不是通用预期值。
[批次实验](../results/batch-size-result.md) · [队列归因](../results/analysis/batch8-cohort-attribution-v1.md)

在同一个 780 会话库上加入条件式具体信息修复，召回从 47.5% 到 60.5%，调用约为三倍。
这测的是**抽取保真度，不是答题正确率**；因此修复保持可选，没有改为服务默认。

## 失败与边界

失败的首要环节随题集和系统版本变化：早期 dev50 的 14 个失败中有 10 个先丢在抽取；
后续 reasoning-48 的 11 个失败中，有 6 个是证据已到达回答上下文但仍答错。
不能把所有错误都归给检索或抽取。
[早期分层](../results/failure-stages.md) · [后续诊断](../results/analysis/v5-offline-gate.md)

来源会话命中不代表答案事实已被抽出；抽取召回提高也不代表端到端正确率提高。
已有的 16 题换问法回放只检验了来源会话能否找回，没有测真实跨月留存或答题质量。
[回放结果](../results/analysis/retention-paraphrase-v1.md)

LongMemEval-S 的 500 题已经全部用于开发或终测。当前代码包含冻结 v2 之后的改动，
但没有新的未见题集端到端成绩；不能把开发数值称作“最新正确率”。
SQLite 与 NumPy 索引也不是跨资源事务，只适合单进程研究与集成环境。
[题集状态](../results/hidden-set-status.md) · [存储边界](../results/storage-boundary-decision-v1.md)
