# v2 产品化实施计划

> 2026-09-13 更新：test100 与归档验证已经完成，旧的“等待冻结结束”前置条件已满足。默认写入、进程内串行访问、demo 清理、REST 凭据身份、主服务导出和在线硬删除均已实现。凭据生命周期、跨资源故障恢复、备份生命周期、账号额度与运维仍待实施；多进程架构按实际部署需要另行推进。以[全部成果与完整计划](PROJECT_RESULTS_AND_PLAN_2026-09-13.zh-CN.md)安排顺序，下文保留较早阶段的目标设计与原始验收要求，不能把其中每一项都视为当前待办或已实现行为。

这份计划只在 `test100` 一次性最终报告完成、实验结论固定之后执行。
它不是当前实验配置的一部分，也不能用来改变已经冻结的 v2 结果。

## 当前边界

`v2-candidate-preingest` 对 `src/`、`scripts/`、`pyproject.toml` 和 `uv.lock`
逐文件哈希。`dev100` 摄取完成并生成 post-ingest freeze 之前，修改认证、删除、
数据库或服务代码都会让已经完成的摄取失去可验证谱系。

因此工作分两条轨道：

| 现在可以做 | 实验结论固定后才能做 |
|---|---|
| 威胁模型、接口契约、迁移设计、验收用例、运维手册草案 | 修改 `src/`、schema、依赖和部署拓扑 |
| 为现有冻结行为补测试 | 引入认证/RLS、硬删除、PostgreSQL/pgvector |
| 定义 RPO/RTO、SLO、保留期和成本预算 | 真实恢复演练、压力测试、密钥轮换和灰度发布 |

“稍后实现”不是因为这些工作不重要，而是为了让研究结论与产品重构保持可归因。

## 为什么要等实验结束

先确认“记忆系统确实有效”，再投入多人账号、安全和运维建设。否则可能把一个
效果还不稳定的实验原型包装成复杂但无用的服务。

## 目标架构与具体工作包

### A. 身份与租户边界

1. 在可信边界验证 OIDC/JWT；把 `issuer`、`subject`、`tenant_id` 和 scopes
   转换成不可由请求正文覆盖的 `ActorContext`。
2. 从所有公开请求模型中移除可自由填写的 `user_id`。REST、MCP 和后台任务都只接收
   `ActorContext`；管理员使用独立 scope，不允许用普通用户入口模拟管理员。
3. 所有持久对象采用 `(tenant_id, object_id)` 复合身份。生产数据库启用行级隔离作为
   第二道防线，应用层过滤不能成为唯一边界。
4. 对 memory ID、session ID、原文搜索、timeline、导出和删除逐一做越权测试；返回 404，
   避免泄露其他租户对象是否存在。

完成门：任何一个 handler、MCP tool 或 repository 方法都不能在没有可信 actor 的情况下
访问状态；跨租户测试覆盖读、写、搜索、删除、导出和后台任务。

### B. 数据生命周期：导出、硬删除和保留期

1. 建立数据清单：session、turn、memory、FTS、evidence、vector、usage、audit、backup。
2. 导出生成版本化、机器可读的归档，包含来源和时间字段，但不包含内部密钥或其他租户 ID。
3. 硬删除使用幂等 job：先记录请求和范围，再在事务中删除关系数据，删除/重建向量与 FTS，
   最后写入不含用户内容的完成证明。
4. 在线数据删除后立即不可检索；备份副本按公开保留期自然到期。不得宣称能从不可变备份中
   选择性擦除，必须准确说明最长残留窗口。
5. 现有 `forget` 保留为“从召回中隐藏”，另设明确命名的 hard-delete 接口，不能混称。

完成门：删除前后自动扫描所有数据面；重复请求不失败；中途崩溃可续跑；恢复旧备份后删除
tombstone 会重新生效。

### C. 存储、并发与幂等

1. SQLite 保留为单机/开发模式；多副本生产模式迁移到 PostgreSQL，并让关系数据、全文索引
   与 pgvector 处于同一事务边界。
2. 每个写请求带调用方 idempotency key，在 `(tenant_id, operation, key)` 上建立唯一约束；
   同一 session 的并发追加使用版本号或行锁，禁止 last-write-wins 静默丢失。
3. 把模型调用与数据库提交分成可恢复状态机：调用结果先持久化，再幂等落库；重试不能重复计费
   或重复生成 memory。
4. 用真实并发压测验证重复请求、相同 session 乱序、worker 崩溃、数据库 failover 和向量一致性。

完成门：至少两个服务进程并发运行；无重复 memory、无跨租户行、无丢失更新；故障注入后可恢复。

### D. 备份、恢复与灾难演练

1. 定义首个目标：RPO ≤ 24 小时、RTO ≤ 4 小时；上线前根据业务重要性重新批准。
2. 自动加密备份数据库、迁移版本和必要配置；模型缓存和可重建索引无需当作唯一真相备份。
3. 每月至少在空环境恢复一次，重建 FTS/向量，并核对行数、随机内容哈希、外键和租户隔离。
4. 演练结果形成带时间、版本、耗时和失败项的 artifact；“备份任务成功”不等于“可恢复”。

### E. 密钥、隐私与审计

1. API key、JWT signing material 和数据库凭据来自 secret manager，不落入镜像、仓库、日志或
   错误响应；定义轮换周期和紧急吊销流程。
2. 默认日志不记录问题文本、memory 内容、token 或原始模型响应；调试内容日志需要短期、显式、
   可审计的开关。
3. 明确数据用途、保留期、地区、子处理方和安全事件流程；权限变更、导出、删除和管理员访问进入
   append-only audit log。
4. 传输加密，数据库和备份静态加密；租户级加密键是否需要单独评估，不提前承诺。

### F. 成本、可靠性与发布

1. usage ledger 以 tenant、operation、model、attempt 计量输入/输出 token、失败、重试和 fallback；
   将预算控制放在调用前，把最终用量写在调用后。
2. 支持 tenant 日/月硬限额、全局熔断和配额告警；价格与模型版本解耦，没有可信价格表时不猜费用。
3. 定义 SLO：可用性、p95 延迟、5xx、模型失败率、队列年龄和配额耗尽时间；每个告警绑定 runbook。
4. 版本化 schema 与 API；expand/contract 数据迁移；灰度发布；一键回退应用版本但不逆向破坏性
   数据迁移。

## 必须通过的关键测试

| 类别 | 最少要证明什么 |
|---|---|
| 隔离 | 账号 A 即使猜到账号 B 的 memory/session ID，也读不到、改不了、删不了 |
| 删除 | 删除前可查到，删除后数据库、全文搜索、向量搜索和原文召回均查不到 |
| 恢复 | 从真实备份恢复后，行数、向量数、哈希关系和权限边界一致 |
| 费用 | 重试、失败和回退请求都正确计量，不重复收费，不漏记 token |
| 并发 | 重复提交只产生一份结果；并发更新不丢失、不交叉到其他账号 |
| 隐私 | 错误信息、结构化日志、指标和备份元数据不包含原始聊天或 API 密钥 |

## 安全设计参考基线

- [OWASP API1:2023 Broken Object Level Authorization](https://owasp.org/API-Security/editions/2023/en/0xa1-broken-object-level-authorization/)：每个使用客户端对象 ID 的入口都必须做对象级授权，不能只比较请求中的用户字段。
- [PostgreSQL Row Security Policies](https://www.postgresql.org/docs/17/ddl-rowsecurity.html)：RLS 可限制每行的查询和修改；启用后无匹配 policy 默认拒绝。生产角色不得拥有 `BYPASSRLS`，表 owner 也要评估 `FORCE ROW LEVEL SECURITY`。
- [NIST SP 800-88 Rev. 2](https://csrc.nist.gov/pubs/sp/800/88/r2/final)：覆盖逻辑与云环境的数据清除、清除方案、结果验证和密码学擦除，是硬删除与备份生命周期设计的当前基线。

## 暂不承诺

- 在单机 SQLite 上直接宣称支持多进程写入；
- 仅靠请求中的 `user_id` 作为真正鉴权；
- 把“软删除 memory 状态”说成用户数据已经彻底删除；
- 没有恢复演练就宣称备份可靠；
- 根据免费额度或过期价格猜测真实费用。

产品化完成后，README 中的“原型”定位才能重新评估。在此之前，v2 的实验指标
只说明测量集上的效果，不代表已经满足真实用户的安全和可靠性要求。
