## 0. Executive Summary

**问题。** LLM 应用要记住用户几个月前说过的事。把全部聊天记录塞进上下文太贵且线性增长；
用向量库检索原始对话片段则无法表达"事实会变"——用户搬过一次家之后，旧地址和新地址会一起
被检索出来，没有机制说明哪个还成立。

**方案。** 把对话压缩成结构化事实（紧凑、可更新、可解释），**同时永久保留原始对话**。
压缩必然有损，本项目不试图消除这个损失，只要求它**可恢复**：结构化记忆不足以回答时，
系统回到原文把那句话捞出来。

**架构。** 两条通路：

- **写入**：对话 → 原文归档 → 两阶段抽取 → 结构化记忆 → 时序消解 → 嵌入 → 索引
- **读取**：查询 → 混合检索 → 候选过滤 → 上下文组装 → 回答器 → 充分性判定 →
  （不足时）原文回退 → 带出处的答案

**最重要的结果。** 在 100 道从未参与任何决策的题上一次性运行：**70.0%** 正确率，
其中 50.0% 来自结构化记忆、20.0% 由原文归档救回，中位上下文 1,468 token。开发集上
同一系统 72.0%，而全量上下文基线 56.0%、普通 RAG 54.0%，上下文分别是它的 75 倍和 9 倍。

**当前最大限制，三条并列：**

1. **保留集上没有基线。**那次只跑了本系统，所以"结构化记忆打平普通 RAG"目前只是开发集结论。
2. **抽取器已知有损且没有修。**批大小 15 每会话产出 2.6 条记忆，批大小 1 是 12.7 条，
   由随机对照确立。所有数字都在这个被压低的天花板之下。
3. **五路检索信号只有一路在生产中生效。**架构支持五路加权融合，冻结配置里
   `semantic=1.0`，其余四路是 `0.0`——而且实测打开它们更差。

## 1. 问题定义与设计目标

### 1.1 方案 A：全量上下文

每次提问把用户全部历史对话原样拼进 prompt。不丢信息，实现只是字符串拼接，没有检索误差。

代价有三层。**成本随历史线性增长**——本项目实测中位 **109,260 token** 一次提问。
**塞进去不等于用得上**——它在开发集上只有 **56.0%**，被上下文小 75 倍的方案打败；长上下文中
信息会被稀释，这是本项目实测到的，不是引用的。**没有事实状态的概念**——用户三年前说住堪培拉、
去年说搬到悉尼，两句都在上下文里，模型每次都要重新推断哪句还成立。

### 1.2 方案 B：对话原文上的普通 RAG

```
对话 → 切成 session / turn 片段 → 每片段算 embedding → 存向量库
查询 → 算 query embedding → 取最相似的 k 个片段 → 拼进 prompt → 回答
```

上下文降到中位 **13,057 token**（约全量的 1/8），实现简单，检索到的是原始措辞——精确的 URL、
型号、数字都原样保留。开发集 **54.0%**。

它天然解决不了三件事。**检索的是"片段"不是"事实"**：一个 session 里可能有二十件事，
只有一件相关，整段都会被拉进上下文。**无法表达事实演化**：向量相似度不知道"我搬到悉尼了"
应该让"我住堪培拉"失效，两条都会被检索到，且旧的可能因为措辞更接近问题而排得更前。
**无法回答跨会话聚合**："我二月份去了几个博物馆"——没有任何单个片段说了这个数字。

### 1.3 方案 C：结构化长期记忆

用 LLM 把对话读成一条条独立的、带类型和时间的事实：

```
原文： "我上个月戒咖啡了，现在改喝抹茶。"
     ↓
记忆： content    = "The user stopped drinking coffee."
      subject    = "user"
      predicate  = "drinks"
      scope      = "profile"
      event_time = 2026-07-15
      update_op  = "replaces"
```

**紧凑**：一条事实几十个 token，中位上下文降到 **1,455**。**可更新**：事实有
`(subject, predicate)` 键，新值可以让旧值失效而不是并存。**可解释**：每条事实都能追回它来自
哪一轮对话，检索时被淘汰的事实也带理由。

### 1.4 根本取舍：压缩是有损的

抽取会丢东西，而且丢的往往正是问题要问的那个标识符。

```
原始助手回复（三个月前）：
  "...I recommend this Mayo Clinic video:
   How to Sit Properly at a Desk to Avoid Back Pain
   https://www.youtube.com/watch?v=UfOvNlX9Hh0 ..."

抽取出的记忆：
  "The assistant recommended a Mayo Clinic resource about desk posture."

今天的提问：
  "What was the Mayo Clinic YouTube video you recommended?"
```

这条记忆**是真的**，而且检索会正确地把它排到第一位——它就是关于 Mayo Clinic 的。但它答不了
这个问题，因为 URL 在压缩中被扔掉了。纯向量库在这里会失败，而且会**一直**失败：重跑、换
embedding 模型、加大 top-k 都没用，因为那个字符串根本不在库里。

**本项目的答案不是"把抽取做得更好"，而是"承认它有损，并保证损失可恢复"：**

> **有损的结构化记忆 + 可回溯的原文归档**

原文永久保存在同一个数据库里，带全文索引。结构化记忆答不了的时候，系统回到原文检索。

#### 必须区分的两种"用原文"

| | **常开挂载**（always-on hydration） | **条件回退**（conditional fallback） |
|---|---|---|
| 何时取原文 | **每次**回答都把记忆对应的原文附上 | **只有**回答器声明记忆不足时 |
| 上下文代价 | 约 **3 倍** | 平均几乎为零（实测触发率 36%） |
| 实测收益 | **+3.2pp**，2 胜 1 负，p = 1.000 | 开发集 **+18.0pp**（54.0% → 72.0%） |
| 当前状态 | 已实现，**降级为不默认启用** | **产品默认路径** |

完整对比见 §6.3。

> ⚠️ 有一处容易读反。本项目另一个结论是"收益来自抽取重写（+29.0pp），而不是常开挂载
> （+3.2pp）"。**这句话说的是常开挂载，不是原文归档。**准确表述：
>
> *两阶段抽取带来了最大的上游改进；常开的原文挂载不值它的 token 成本；而条件回退承担的是
> 另一个角色——只在结构化记忆不足时把压缩丢掉的细节找回来。*
>
> 在开发集上，原文归档独立贡献了 18.0 个百分点。它不是可有可无的装饰。

### 1.5 设计目标

| 目标 | 可检验的形式 |
|---|---|
| 紧凑 | 上下文比全量转录低一个数量级以上 |
| 可更新 | 同一 `(subject, predicate)` 的新值能让旧值退出检索，且旧值不被删除 |
| 可恢复 | 抽取丢掉的细节，能通过原文路径答出来 |
| 可解释 | 每条记忆能追到来源轮次；每个**遗漏**有明确理由 |
| 隔离 | 跨用户读写不可能，猜到 id 也不行 |

## 2. 系统架构

```
                          ┌──────────────────────┐
                          │      Conversation     │
                          └───────────┬──────────┘
                                      │
        ┌─────────────────────────────┴─────────────────────────────┐
        │                     WRITE PATH                            │
        │                                                           │
        │   turns 表（原文归档）          Stage A：抽事实串          │
        │   sessions 表                          ↓                  │
        │   turns_fts（BM25 索引）        Stage B：配 key + update_op│
        │        │                               ↓                  │
        │        │                        memories 表               │
        │        │                     （双时间 + 出处锚点）         │
        │        │                               ↓                  │
        │        │                    时序消解（supersession）       │
        │        │                               ↓                  │
        │        │                    嵌入 → NumpyFlatIndex (.npy)  │
        └────────┼──────────────────────────────┬───────────────────┘
                 │                              │
        ┌────────┼──────────────────────────────┼───────────────────┐
        │        │          READ PATH           │                   │
        │        │                              │                   │
        │  Query ─────────────────────────→ 混合检索                │
        │        │                        （5 路信号，融合打分）     │
        │        │                              ↓                   │
        │        │                     候选过滤 + top_k 截断         │
        │        │                              ↓                   │
        │        │                        上下文组装                 │
        │        │                   （v1 平铺 / v2 会话连贯）        │
        │        │                              ↓                   │
        │        │                        回答器（1 次调用）         │
        │        │                              ↓                   │
        │        │                    status ∈ {answer,             │
        │        │                     need_source, no_evidence}    │
        │        │                     ┌────────┴────────┐          │
        │        │                  answer          need_source     │
        │        │                     ↓                 ↓          │
        │        └──────────────────→  │          原文回退检索       │
        │                              │        （BM25 over turns）  │
        │                              │                 ↓          │
        │                              │         回答器（第 2 次）   │
        │                              └────────┬────────┘          │
        │                                       ↓                   │
        │                            答案 + 出处 + 被拒理由          │
        └───────────────────────────────────────────────────────────┘
```

**写入通路**（§3）：原文归档 → 两阶段抽取 → 时序消解 → 存储与索引。离线批量进行，
每 15 个会话花 2 次 LLM 调用。

**读取通路**（§4 检索、§5 回答）：检索 → 上下文组装 → 回答 → 必要时回退。
一次提问默认花 **1 次**回答器调用；只有回答器自己声明记忆不足时才花第 2 次。

## 3. 记忆的写入与更新

### 3.1 原文归档

**解决什么。** 抽取有损（§1.4）。原文不保存，损失就是永久的，系统在"记忆里没有"和
"这件事没发生过"之间无法区分。

**输入**一个会话（有序的 `(role, content, timestamp)` 串），**输出**写进两张表并自动建立
全文索引：

```sql
sessions(id PK, user_id, started_at, source)
turns(id PK, session_id FK→sessions, turn_index, role, content, ts)
INDEX idx_turns_session ON turns(session_id, turn_index)
```

`turns` 表**没有 `user_id` 字段**。用户归属通过 `session_id` 外键 join 到 `sessions` 获得。
这不是疏忽：任何绕过 join 的查询都拿不到用户信息，**隔离靠 schema 而不是靠每处查询记得加
条件**。原文全文检索因此必须三表 join（`store/sqlite.py:378`）。

**出处锚点。** 每条记忆带四个字段指回原文：`source_session_id`、`source_turn_index`、
`source_char_start`、`source_char_end`。"这条记忆怎么来的"可以精确回答到字符区间。
在干净的 P10 store 上 **4,843 / 4,843 条记忆全部能解析到来源轮次**——这是条件回退的前提，
因为回退第一级就是"取回这些记忆锚定的原文轮次"。

**为什么这是存储决策而不是检索算法。** 保留原文和"怎么找到原文"是两个独立问题。前者是
schema 决定，一旦不做就无法事后补救；后者（source-local 查找、BM25、稠密、混合）可以随时
替换，本项目确实换过一次实现（§5.5）。混为一谈会导致一个常见错误：因为"我们已经有向量检索了"
就不保存原文。

**限制。** 数据库体积——train150 的 `.db` 是 185MB，大部分是原文。内容策略拒绝的会话原文仍
保留但没有记忆，这类会话单独计数（heldout100 上 1 个）。

### 3.2 两阶段抽取

**解决什么。** 把自然语言对话变成结构化、可检索、可更新的事实。输入是 15 个会话一批
（`ingest.sessions_per_request: 15`），输出是一组 `Memory` 行。

#### 一个完整的例子

```
── 输入 turn ─────────────────────────────────────────────
session s_4f2a, turn 3, role=assistant, ts=2026-05-02
"Since you mentioned your desk setup, I recommend this Mayo Clinic
 video: How to Sit Properly at a Desk to Avoid Back Pain
 https://www.youtube.com/watch?v=UfOvNlX9Hh0"

── Stage A（裸事实串，1 次 LLM 调用 / 批） ─────────────────
{ "session_index": 0,
  "fact": "The assistant recommended a Mayo Clinic video about desk posture." }

── Stage B（配 key，1 次 LLM 调用 / 批） ───────────────────
{ "temporal_key": "assistant_recommendation",
  "update_op":    "coexists",
  "object":       "Mayo Clinic desk posture video" }

── 规则补齐（0 次调用） ────────────────────────────────────
type=episodic  entities=[mayo clinic]  importance=0.5
event_time=2026-05-02（从 turn 的 ts 解析）
source_session_id=s_4f2a  source_turn_index=3  source_char_start/end=…

── 最终 memory 行 ─────────────────────────────────────────
content     "The assistant recommended a Mayo Clinic video about desk posture."
subject     "assistant"        ← 这条事实是关于谁的
source_role "assistant"        ← 谁说的
predicate   "assistant_recommendation"
object      "Mayo Clinic desk posture video"
scope       "recommendation"
update_op   "coexists"
status      "active"
```

URL 在 Stage A 就丢了。这就是 §1.4 的有损压缩，条件回退存在的全部理由。

#### 为什么分两阶段

Stage A 只负责"这段对话里有哪些值得记的事实"，Stage B 只负责"给这条事实配一个时序键，
并说明它对历史事实做了什么"。两次调用而不是一次，每批成本从约 190 次请求涨到约 380 次。

理由是 Stage B 的替代方案**被实测过**：正则实现（`_rule_keying`，代码保留可运行）在 148 条
真实记忆上只有 **43% 的谓语准确率**，且**产生了 0 次覆盖**。正则无法给开放域关系配键。
而把两阶段合并成一次调用的问题是：单次调用的输出预算要同时承载"读懂十五段对话"和"为每条
事实设计一个键"，而位置衰减实验（§6.4）表明输出预算正是这个模型的瓶颈。

**规则保留在它们有优势的地方**：`type`、`entities`、`importance`、日期解析全部用规则，
不花 LLM 预算。Stage B 的整个输出预算只用在正则做不到的那一部分。

#### 当前限制

批大小 15 是当时的配额约束下的选择：免费额度每模型每天 500 次请求，2,400 个会话在批大小 15
下是 189 个批次 / 378 次抽取调用，能在一天内跑完。

**后来的随机对照证明这个配置在丢信息**：同一段对话挪到批次后面，产出只剩三分之一；
批大小 1 相对批大小 15 是 4.7 倍产出、零产出率从 11.7% 降到 0.0%。完整实验见 **§6.4**。

配置没有改，因为改了意味着所有 store 重建（免费额度下多花 28 个配额日），而实验结论还没冻结。
**本项目所有数字都产生在这个已知有损的抽取器之上——这是一个被压低的天花板，不是一个未知数。**

### 3.3 记忆的 Schema

关键字段（完整 20 余个字段见 **附录 A**）：

| 字段 | 含义 |
|---|---|
| `user_id` | 命名空间。每次读都必须带，隔离的实施点 |
| `content` | 人读的那句话，也是被嵌入和被 BM25 索引的文本 |
| `subject` | **这条事实关于谁** |
| `predicate` | 时序键。覆盖检测匹配 `(user_id, subject, predicate)` |
| `object` | 谓语的值 |
| `source_role` | **谁说的**：`user` / `assistant` / `system` |
| `scope` | 为什么值得留：`profile`/`preference`/`plan`/`recommendation`/`commitment`/`shared_context`/`event` |
| `event_time` / `valid_from` / `valid_to` | 有效时间轴 |
| `ingested_at` | 记录时间轴 |
| `replaces_previous` / `update_op` | 替换信号与 Stage B 的判定 |
| `status` / `superseded_by` | `active` / `superseded` / `evicted` |
| `source_session_id` / `source_turn_index` / `source_char_start` / `source_char_end` | 出处锚点 |

#### 为什么"谁说的"和"关于谁"必须是两个字段

三句话都由用户说出：

| 原句 | `source_role` | `subject` |
|---|---|---|
| "我住在悉尼。" | user | user |
| "Andy 穿了蓝衬衫。" | user | **andy** |
| （助手说）"我推荐 Mayo Clinic 那个视频。" | **assistant** | assistant |

只有一个字段的话第二行无处安放——它既不是关于用户的，说话人也不是 Andy。而这一对字段是
"你之前推荐了什么"这类问题能被回答的前提：这个问题过滤的是 `source_role='assistant'`，
跟 subject 的任何属性都无关。

### 3.4 双时间表示

两条独立的时间轴，从第一次迁移就存在：

| 轴 | 字段 | 回答的问题 |
|---|---|---|
| **有效时间** | `event_time`, `valid_from`, `valid_to` | 这件事**在世界上**什么时候成立？ |
| **记录时间** | `ingested_at` | 我们**什么时候知道**的？ |

```
2026-03-01  用户说："我上个月搬到悉尼了。"
    event_time / valid_from = 2026-02   （搬家实际发生）
    ingested_at             = 2026-03-01（系统知道）
```

只有一条轴的话两个问题会互相污染："我二月份住在哪"要按有效时间查，"系统三月一号之前知道吗"
要按记录时间查。而且用户经常追溯地陈述过去（"我上个月……"），这时两条轴的顺序甚至可以相反。
**覆盖逻辑排序用的是 `event_time` 而不是 `ingested_at`**——否则"我上个月搬到悉尼"会被更早
录入但描述更早事件的记忆盖掉。

从第一天就加的理由（`DECISIONS.md` D9）：事后补时间维度要重写所有历史行，而重建一个 store
要花几小时配额；一开始留着几乎不花成本。

### 3.5 覆盖（Supersession）

**解决什么。** "我住堪培拉"和"我搬到悉尼了"都是真话，只有一条现在成立，检索必须知道是哪条。

**机制**（`temporal/resolve.py:195`）：

```
1. 取该键下全部记忆（含 superseded）。少于 2 条 → 返回。
2. 判断可消解性：is_single_valued(predicate) 或 任意一条带 replaces_previous。
   都不满足 → 进入修复分支，返回。
3. 只保留有 event_time 的；不足 2 条 → 返回（无日期计入 skipped_undated，不猜测）。
4. 按 (event_time, id) 排序。
5. 把连续的等值记忆折叠成"运行段"：同一值被重复陈述时，最早那条拥有整个区间。
6. 逐段处理：只有当【下一段的首条】自己带 replaces_previous 时，才关闭当前段的有效期。
```

**第 6 步的逐条判定不能被汇总成逐键判定**——早先的实现只要"这个键可消解"就把链上每一对连续
记忆都退休，线上因此把两句都为真的话错误地互相取代（事故记录见**附录 D**）。Stage B 的判定
单独测试时误覆盖率是 0%，损失全部发生在集成层。

**第 2 步的修复分支**同样重要：如果一个键曾在错误的判断下被消解过，它的事实此刻正躺在
`superseded` 状态、对检索不可见。所以发现这个键其实不可消解时，代码会把它们**恢复成 active**
而不是仅仅跳过——否则一次错误判断会永久留在每一个已经建好的 store 里。

**两条判据的关系。**

```python
SINGLE_VALUED_PREDICATES = frozenset({"lives_in", "works_as", "works_at", "uses_framework"})
```

只有四个词，刻意保守：一个错误的覆盖会让**还成立的事实**从所有后续查询里消失，而一个漏掉的
覆盖只是让 store 退化成平铺列表。**不对称的代价决定了不对称的默认值**，默认是 `coexists`。
`update_op` 就是为了取代这个手工列表而引入的——直接问模型"这条事实对历史做了什么"，
而不是靠谓语名字去猜。

#### 当前限制：替换信号被谓语命名冲散

覆盖按精确的 `(user_id, subject, predicate)` 三元组匹配，而抽取器给每条事实现编一个谓语字符串。
结果是信号和它该替换的事实落进同一命名空间下的**不同键**：

| | heldout100 | train150 |
|---|---:|---:|
| 带 `replaces_previous` 的记忆 | 622 | 902 |
| …独占一个键（无对象可替换） | **546（88%）** | **777（86%）** |
| …其 `(user,subject)` 下**还有别的谓语** | **525（96%）** | **757（97%）** |
| 实际被覆盖 | 42 | 76 |
| 信号 : 效果 | **14.8 : 1** | **11.9 : 1** |

全库 **55.6%**（heldout100）/ **55.1%**（train150）的记忆落在多值且永远无法覆盖的键上。
直接佐证：同一命名空间同一 subject 下有 **17 组单复数撞名**（`assistant_recommendation` vs
`assistant_recommendations`、`aquarium` vs `aquariums`）。同一个概念，两个键，互相看不见。

**这是有证据的机制假设，不是已证明的原因。**它解释了信号与效果 12–15 倍的落差，也与
`knowledge-update` 五个失败的形状吻合（§6.7），但还没有实验把单个失败连到键形状上。
谓语归一化列在 §8.3。

## 4. 存储与检索

### 4.1 存储布局

SQLite 是一个**链接进应用进程的 C 库**，不是数据库服务器：没有服务进程、没有端口、
没有网络协议，整个数据库就是磁盘上的一个文件，Python 进程内的库直接读写它。因此本项目的
并发能力由进程模型决定，而不是由数据库配置决定。调用链是
`FastAPI → MemoryService → SQLiteMemoryStore → sqlite3 → stores/<name>.db`，
中间没有进程间通信。

| 产物 | 路径 |
|---|---|
| 主数据库 | `stores/<name>.db`（train150 为 185MB） |
| 向量矩阵 | `stores/<name>-index.npy`（float32） |
| 向量 id 表 | `stores/<name>-index.ids.json`（行号对应） |
| 摄入检查点 | `stores/<name>-ingest.json` |

Docker 下 `./stores` 绑定挂载到 `/data/stores`，容器内外是同一个文件——compose 注释指出这是
为了开发时容器和本地 `lltm` 看到同一份数据，而这**恰恰是生产不该做的**，因为 SQLite 单写。

主要的表：`sessions` / `turns`（原文）、`memories`（结构化记忆）、
`memories_fts` / `turns_fts`（FTS5 倒排索引）、`entities` / `memory_entities`（实体信号数据）、
`evidence`（合并出的记忆由哪些原始记忆支撑）、`meta`（store 级元数据，含抽取器指纹）。

**WAL。** `schema.sql` 第一行是 `PRAGMA journal_mode = WAL`。写事务期间主 `.db` 不动，
新页追加到 `-wal` 文件，读者不被阻塞；`-shm` 是让多个连接知道哪一页最新的共享内存索引；
checkpoint 把 `-wal` 合并回主文件。**WAL 解决的是读写并发，不是写写并发**——SQLite 任何时刻
仍然只允许一个写事务。因此摄入和评测都要先取得 `locking.py` 的跨进程咨询锁（起因见附录 D）。

**索引。**

```sql
idx_mem_user_status  (user_id, status)
idx_mem_sp           (user_id, subject, predicate) WHERE status='active'   -- 部分索引
idx_mem_type         (user_id, type, status)
idx_mem_valid        (user_id, valid_from, valid_to)
```

`idx_mem_sp` 是**部分索引**：覆盖检测只关心还成立的事实，把已失效的行排除在索引外。

### 4.2 词法检索

FTS5 虚拟表背后是倒排索引（`"coffee" → [memory_42, memory_87, …]`），查询不需要扫全表。
本项目的定义：

```sql
CREATE VIRTUAL TABLE memories_fts USING fts5(
    content, content='memories', content_rowid='rowid', tokenize='porter unicode61');
```

三个细节：`content='memories'` 是**外部内容表**，FTS5 只存倒排索引不复制正文，查询时靠
`rowid` 回主表取；`porter unicode61` 按 Unicode 切词折叠大小写并做词干还原，
`drinking`/`drinks`/`drink` 归一；外部内容表不会自动跟随主表，所以 schema 为 `INSERT`、
`DELETE`、`UPDATE OF content` 各定义了触发器维护索引。`turns_fts` 有一组对应的。

排序直接用 FTS5 内置的 `bm25()`，**本项目没有自己实现 BM25**：

```sql
SELECT m.id, bm25(memories_fts) AS score
FROM memories_fts JOIN memories m ON m.rowid = memories_fts.rowid
WHERE memories_fts MATCH ? AND m.user_id = ? AND m.status = 'active'
ORDER BY score LIMIT ?          -- bm25() 是负数，越负越好
```

⚠️ **FTS5 的 `bm25()` 返回标准分数的负数**，所以"最相关"对应最小值、`ORDER BY` 是升序。
公式与变量见**附录 B**；$k_1$ 和 $b$ 由 FTS5 内部固定，本项目未配置，
**当前材料无法确认其具体取值**。

两个索引各自的用途：`memories_fts` 供混合检索的词法那一路，`turns_fts` 供原文回退的档案级
检索（§5.5）。

### 4.3 语义检索

嵌入在**本机**跑，模型 `all-MiniLM-L6-v2`，维度 **384**。理由是配额：全语料嵌入约 5,300 万
token，而每日请求数正是绑定约束，放到 API 上会和抽取抢同一个池子。

**归一化做了两次**（代码确认）：编码器 `normalize_embeddings=True`，索引在 `add()` 和
`search()` 里又各归一化一次。注释写明这是刻意冗余——"放在这里而不是编码器里，这样每个后端
都得到同样的保证"，即索引不信任上游。因此 $\lVert\mathbf q\rVert=\lVert\mathbf m\rVert=1$，
`scores = self._vectors @ q` 这一行**直接就是余弦相似度**。

**精确搜索**（`store/vector.py`）：

```python
scores = self._vectors @ q  # (n, 384) @ (384,) → (n,)
k = min(limit, len(self._ids))
top = np.argpartition(-scores, k - 1)[:k]  # O(n) 选前 k，不排序
top = top[np.argsort(-scores[top])]  # 只对这 k 个排序
```

一次矩阵-向量乘法算出全库分数，再用 `argpartition` 做 O(n) 的 top-k 选择，避免对 n 个元素
全排序。

**向量文件与 SQLite 是两个文件**，一致性靠流水线而不是事务保证。因此有一个只读状态检查
（`scripts/check_ingest_state.py`），每次恢复摄入前联合校验 checkpoint / 原文归档 /
SQLite 完整性 / 记忆数 / 索引 id / 向量行数 / 抽取器指纹。train150 上这七个数字全部吻合
（18,519 = 18,519 = 18,519，维度 384）。

### 4.4 检索打分

融合公式（各信号定义与变量说明见**附录 B**）：

$$S(m,q) = w_s S_{\text{sem}} + w_l S_{\text{lex}} + w_r S_{\text{rec}} + w_i S_{\text{imp}} + w_e S_{\text{ent}}$$

| 信号 | 定义要点 |
|---|---|
| semantic | $(\cos+1)/2$，把 $[-1,1]$ 搬到 $[0,1]$ |
| bm25（词法） | 对**本次查询实际观察到的候选**做 min-max，`lower_is_better=True` |
| recency | 指数半衰，$H=$ `recency_halflife_days`，默认 30 天 |
| importance | 直接取写入时赋的 $[0,1]$ 值 |
| entity | 取**最大**而非平均：一个实体完全命中就够 |

BM25 的归一化是**相对**的：它衡量"在本次候选里排多好"，不是绝对相关性；所有候选都很差时，
最差里最好的那个仍拿 1.0。`hybrid.py` 的注释明确说这不是美化——FTS5 的值是负的、无上界，
直接相加会让词法项**按实现细节而不是按配置的权重**去支配或消失。

排序键是 `(-score, -semantic_raw, memory.id)`，保证同一 store 和同一查询永远产生同一上下文；
一个会随运行变化的上下文，与它试图减少的回答器方差不可区分。

#### ⚠️ 生产配置里只有一路信号在起作用

`config.py` 的默认权重是 `semantic 1.0`，`bm25 / recency / importance / entity` 全是 `0.0`，
而 `configs/fallback.yaml` 的 `retrieval:` 块只设了 `top_k: 20`，没有覆盖任何权重。所以

$$S(m,q) = 1.0\cdot S_{\text{sem}} + 0 + 0 + 0 + 0 = S_{\text{sem}}$$

**"架构支持"和"生产启用"是两件事。**五路信号在每次检索时都被**计算并记录**（出现在
`signals` 字段里，Inspector 和 API 的 `explain` 都能看到），但只有语义一路有非零权重。
另外四路已在 §6.5 中测量——**打开它们全部更差**。

一个后果：BM25 仍然影响**候选集**（词法命中会并入候选），只是不影响**排序**。所以词法路径
的作用是召回而不是排序。

### 4.5 为什么是这套，而不是别的

按本项目的实际规模比：单机、单进程写入、最大 store 18,519 条记忆 / 185MB、并发需求为零。

| 方案 | 为什么不用 |
|---|---|
| **PostgreSQL** | 需要常驻服务、连接配置、迁移工具。并发需求为零，付出的是每个开发者和每次 CI 都要起一个数据库。**一旦做多租户生产部署，这是第一个要换的东西** |
| **pgvector** | 同上；且 18k × 384 float32 ≈ 27MB，精确搜索毫秒级，索引结构买不到东西 |
| **Elasticsearch** | 一个 JVM 服务、集群运维、以及一份数据副本。`schema.sql` 的注释写得直接：FTS5 免费给了 BM25，替代方案是搭一个 ES，"在这个规模上不值一个服务依赖" |
| **外部向量库** | 引入第二个持久化系统，于是记忆行和它的向量分处两地，需要跨系统一致性。本项目的删除、命名空间隔离、`status` 过滤全部依赖它们在同一个事务里 |
| **FAISS / HNSW / IVF** | `IndexFlatIP` 就是暴力内积扫描，跟那行 `@` 一样，而瓶颈是 LLM 调用。近似索引被排除的理由不同：**它们的召回噪声与记忆算法本身的回归不可区分**，会污染整张消融表 |

**取舍一句话**：当前选择用"无法多写"换来了"零运维、单文件、可整体复制、可 checksum、
可在 CI 里凭空创建"。对一个每个实验都要冻结、哈希、复现的项目，最后几条是主要收益。
变成多租户服务时这个取舍就反过来。

## 5. 回答流水线

全程跟踪一个具体查询：`user_id="alice"`，
`query="What was the Mayo Clinic YouTube video you recommended?"`

### 5.1 候选过滤

查询文本走两条路：语义那一路 `encoder.encode_one(query)` 得到 384 维已归一化向量；
词法那一路经 `_fts_match()` 转成 FTS5 的 MATCH 表达式。用的是同一个编码器和同一个模型——
查询和记忆被映射进同一个向量空间，这是"相似度"有意义的前提。

```
全库向量搜索
   → 过滤 user_id ≠ namespace          （命名空间隔离）
   → 过滤 status = 'evicted'           （已删除）
   → 时序模式下只留 status = 'active'  （已被覆盖的不参与）
   → 截断到 candidate_limit = 50
   ∪  BM25 前 50
   → 五路打分、排序
   → （可选）重排
   → 截断到 top_k = 20
```

顺序很重要：语义那一路先在整个索引上搜索，**过滤之后**再截断——先截断再过滤会让被过滤掉的
行白白占用名额。

**被拒的记录也要返回。** API 的 `explain` 模式返回一个 `rejected` 列表，每条带理由：
`superseded`（这条事实已经不成立）或 `below_rank`（仍然成立，分数没进 top_k）。设计理由是
**一个没有理由的"没有结果"，跟一个 bug 长得一模一样**。同样的原则出现在上下文组装的
`dropped_sessions` 和检索追踪的 `RetrievalTrace` 里。

**分阶段召回追踪。** `RetrievalTrace` 记录截断和重排**之前**的完整候选集。一个端到端的召回
数字无法区分"某阶段没找到"和"某阶段把找到的删掉了"：候选召回 100% 而重排后 90%，说明重排器
在删正确证据——这跟找不到是完全不同的问题。这个仪表是 §6.7 里能给每个模块算 oracle 上限的基础。

### 5.2 上下文组装

**v1 是平铺 top-k**：20 条记忆按分数拼成一个列表。问题是**单条相关 ≠ 连贯的推理上下文**——
三月自行车维修的一条记忆可能夹在六月雕塑课的两条之间，跨事件的问题拿到的是被打散的时间线。

**v2 是会话连贯上下文**，从检索结果重建同样的形状，不用 gold 标签：

```
检索结果 → 按 source_session_id 分组 → 每会话聚合成一个会话分 → 会话按分排序
  → 取前 max_sessions 个
  → 每个会话内部：取出该会话【全部】active 记忆，按事件顺序排
  → 可选：只保留最佳命中前后 window_radius 条
  → 全局硬上限 max_total_memories，超了就【整个会话】不要
  → 会话之间按时间顺序铺开
```

会话聚合支持 `max` / `sum` / `mean` / `sum_top3` 四种（公式见附录 B）。两条设计约束都有明确
理由：**窗口按事件顺序连续而不是按分数**——"周围的事情解释了这件事，一个按分数拼出来的窗口
只是一个更小的平铺排序"；**要么整个会话要么不要**——硬上限触发时跳过整个会话而不是截断它，
因为半条时间线正是这个机制要摆脱的形状，被跳过的会话记进 `dropped_sessions`。

**当前配置。** `configs/v2.yaml` 的 context 块是 `mean` 聚合、`window_radius=1`、
`max_total_memories=30`、`max_sessions=3`、按时间顺序。它由固定规则从七组网格中选出，
选型过程见 §6.6。

### 5.3 记忆如何呈现给回答器

不是裸列表，而是**按 `scope` 分组加小标题**（`runners/memory.py :: render_grouped`）：

```
About the user:
- The user lives in Sydney.

User preferences:
- The user prefers turbinado sugar in baking.

Previously recommended by the assistant:
- The assistant recommended a Mayo Clinic video about desk posture.

Other people and things discussed:
- Andy wore a blue shirt to the meeting.
```

**为什么分组。** 一条约束（"用户对坚果过敏"）和一个候选答案（"用户喜欢杏仁蛋糕"）在裸列表里
长得一样。加了小标题之后，模型知道前者是**用来约束回答**的，后者是**可以被推荐**的。
预 P10 的记忆没有 scope，代码检测到全部无 scope 时退回裸列表——不猜测、不编造。
完整标题映射见附录 A。

### 5.4 充分性判定

system prompt（`memory-aware-v2`）分四段：这些记忆是关于用户的上下文，不一定是问题的直接
答案，能用就显式用上；问具体事实而没有记忆包含它就说不知道；**但不要仅仅因为没有记忆一字
不差地写出答案就拒答**；直接、简洁地回答。第二段和第三段后半句是一次真实修复的产物（§6.7）。

第一次调用返回的**不是散文，而是一个结构化判定**：

```python
status: Literal["answer", "need_source", "no_evidence"]
answer: str  # status == "answer" 时的回复
reason: str  # 缺什么，一句话
source_query: str  # need_source 时：用什么关键词去搜原文
```

| status | 含义 | 后续 |
|---|---|---|
| `answer` | 记忆足够 | 直接返回，**总共 1 次 LLM 调用** |
| `need_source` | 有记忆切题，但问的那个具体细节（URL、精确数字、产品名）没被保留 | 触发原文回退 + **第 2 次**调用 |
| `no_evidence` | 提供的东西跟问题无关 | 触发原文回退（档案级） |

**为什么要结构化判定。** 只返回散文，就只能在"每次都附原文"（3 倍上下文换不到可测收益）和
"永远不恢复"之间二选一。让模型说出它**处在哪一种情况**，第二次调用就只为 `need_source` 付费。
这是把 §1.4 的取舍变成一个运行时决策。

### 5.5 条件式原文回退

这是本项目最有特点的部分之一。

**输入**：`user_id`、`source_query`（回答器自己给的关键词）、本次检索到的记忆。
**输出**：一个 `RawEvidence`——几条原文轮次、用的哪一级、以及理由。

| 级别 | 来源 | 适用 |
|---|---|---|
| `source_local` | 检索到的记忆所锚定的原文轮次 | 检索找对了记忆，只是细节没保住 |
| `archive_wide` | 对整个命名空间的 `turns_fts` 做 BM25 | 抽取整个漏掉了这段对话 |
| `none` | 两边都没有 | 仍然回答"不知道" |

**机制**（`retrieve/fallback.py :: recover`）：

```python
ranked = store.search_turns(user_id, query, limit=pool)  # pool = max(15, max_turns*5) = 15
local = store.turns_for_memories(memories)
found_the_conversation = bool(local) and (not ranked or ranked[0].session_id in local_sessions)
```

关键判据是：**本次查询的最佳证据，是否落在检索到的记忆所指向的那个会话里。**是 → 记忆找对了
对话只是丢了细节，用 `source_local`，并**按档案排序给这些本地轮次排序**再截断；否 → 抽取整个
漏掉了那段对话，用 `archive_wide`。

**为什么按会话判定而不是按轮次**：同一段对话里 BM25 经常更偏爱**用户的提问**而不是**助手的
回答**，因为提问会重复查询本身的词。按轮次粒度判定会把这读成"档案赢了记忆"，从而抛弃一个
其实已经找对地方的记忆。

**没有任何一级授权编造。** 档案里也没有时，正确答案仍然是"我不知道"。拒答率是一个被测量的
优点（本系统 100%，全量上下文 50%），一个把未命中变成自信猜测的回退会把它换掉。

当前配置 `max_turns=3`、`max_chars=2400`，渲染成
`[session <id> · turn <index> · <role>]` 加原文。

**回退到底贡献了什么：**

| | dev50 | heldout100 |
|---|---:|---:|
| 只靠结构化记忆答对 | 54.0% | 50.0% |
| 被原文归档救回 | **+18.0pp** | **+20.0pp** |
| **最终正确率** | **72.0%** | **70.0%** |
| 回退触发率 | 32% | 36% |
| 触发后答对的比例 | 56.2% | 55.6% |

**结构化记忆单独跑正好打平 `naive_rag`（54.0%）。归档是把产品拉到基线之上的那一半。**
把 72.0% 整个引用而不拆分，会读成好像记忆层答对了全部——本报告不这样写。

**限制**：`max_turns` 从未扫过；已知一个案例（`omelette`）的答案在 BM25 第 6 位，说明取多深
是一个独立的开放问题。这个组件的实现曾被一次事故重写过，记录在附录 D。

## 6. 评测与实验

全项目的实验集中在这一章，按被检验的设计问题组织，不按开发日期。每个实验固定写：
假设 → 对照 → 处理 → 指标 → 结果 → 解读 → 决定。**"没有采用"也是实验结果。**

### 6.1 评测协议

**基准：LongMemEval-S。** 500 道题，每题配一份几十个会话的"干草堆"，其中只有少数含答案。
六类题：`single-session-user`、`single-session-assistant`、`single-session-preference`
（gold 是一段**评分标准**而不是参考答案）、`multi-session`、`temporal-reasoning`、
`knowledge-update`。选它不选 LoCoMo 的理由：前者有真实的多会话时间跨度和显式类型划分，
后者的会话是合成的（D1）。

**基线。** `full_context` 是参考点**不是天花板**（D16）——它在 dev50 上 56.0%，证明"全塞进去"
本身不解决问题；`naive_rag` 是真正的对手。

**数据集分工，本项目最重要的一条方法论。** dev50 只撑了两周就不能用了，原因不是它小：

> 在普通监督学习里训练集吸收拟合，验证集只被少数几个模型选择决策碰到——那是一条很窄的通道。
> 这里**拟合的形式是 prompt 工程**，而 prompt 是靠**逐题读 dev50 的失败**写出来的：抽取
> prompt 从它们重写，回退设计从它们选定，闸门和阈值在它们上面调，六个模块因为它们被砍掉。
> 50 道题同时干着训练和验证两份活，走的还是最宽的通道。

**这就是 prompt tuning 泄漏验证集的机制**：不需要梯度，只需要有人反复读同一批失败。

冻结的协议（2026-08-20，已验证两两交集为空、并集正好 500）：

| 集合 | n | 角色 | 能逐题看失败吗 |
|---|---:|---|---|
| `dev50` | 50 | v1 开发 —— **已烧穿** | 只作历史 |
| `heldout100` | 100 | v1 最终测试 —— **已花掉**，70.0% | 已花掉，再看不额外付出 |
| `train150` | 150 | **v2 开发** | **可以，不设限** |
| `dev100` | 100 | **v2 验证** | **不行**，只看聚合指标 |
| `test100` | 100 | **v2 最终测试** | **不行**，那一次运行之前不许看 |

**预注册。** 每个实验在跑之前写下臂、指标、决策规则和一条注册的预测（`results/prereg-*.md`）。
决策规则由代码在跑完之后自动套用，写出哈希绑定的决策文件，**没有事后重新解释的余地**。
一个具体收益：heldout100 单跑 70.0%、三次均值 71.3%，预注册要求报告单跑那一枪，
**所以这个项目亏了 1.3 个点**。预注册值钱就值钱在这个方向上。

**重复运行。** heldout100 三次给出 70 / 71 / 73，极差 3；三次全对 69、三次全错 25、
**不一致 6**。协议因此改成：100+ 规模在方差被刻画过之后单跑可作标题数字；
**几十道题规模的配对结论必须每臂 k 次运行并报出一致率**。这条**追溯适用**——
仓库里每一个早于 2026-08-20 的配对结论都是单次运行。

**报告哪些指标**：准确率、分题型准确率（每格 3–27 题，**只作描述**）、分阶段来源会话召回、
中位上下文 token、回退触发率与触发后正确率、API 请求与 token、运行间一致率。

### 6.2 抽取：v1 单阶段 vs 两阶段

| | |
|---|---|
| **假设** | 抽取质量是记忆系统的瓶颈 |
| **对照 / 处理** | `chronomem`（v1） / 两阶段 + schema 拆分 + prompt 加示例 |
| **指标** | 配对准确率（31 题先导） |
| **结果** | **+29.0pp**，11 胜 2 负，**p = 0.022** |
| **解读** | 全项目最大的单项增益。两臂来源会话召回都是 93.5%，所以增益不可能来自检索 |
| **决定** | 采用 |

v1 只有 **26.0%**，被普通 RAG 打了 28 个点，两个原因：**用规则描述该抽什么，模型不照做**
（改成带示例后，来源保真度从 33.6% → 36.6%，而且*唯一没有配示例的那条指令，正是模型一直
不执行的那条*）；**`subject` 退化成说话人开关**（v1 只有 0.6% 的记忆 `subject='assistant'`，
两阶段是 6.7%），第三方事实无处安放，可观测后果是 `single-session-assistant` 全类 0/4
而两个基线都是 4/4——这么整齐的差距不可能是排序问题。

### 6.3 证据策略：纯记忆 / 常开挂载 / 条件回退

| | |
|---|---|
| **假设** | 给回答器附上原文证据会提高准确率 |
| **对照** | 纯记忆 |
| **处理 1 / 2** | 常开挂载（`two_stage_hydrated`） / 条件回退 |
| **指标** | 配对准确率 + 中位上下文 token |
| **结果** | 挂载 **+3.2pp**，2 胜 1 负，p = 1.000，**3 倍上下文**；回退 **+18.0pp**（54.0% → 72.0%），9 胜 1 负 |
| **解读** | 挂载的收益不可区分于零而成本确定；回退把同一笔钱只花在需要的 36% 上 |
| **决定** | 挂载降级为非默认；条件回退成为产品路径 |

回退臂与基线只在三个 `fallback` 配置项上不同，运行前检查过而非事后声称。配对精确 McNemar
`p = 0.022`。

> ⚠️ **这个 p 值不成立。**它是每臂单次运行，而且是在同一批暴露了那个缺陷的 50 道题上测的
> （缺陷修复把该臂从 66.0% 抬到 72.0%）。按实测每 100 题翻转 6 道算，50 题上**一次翻转**
> 就把 9 胜 1 负变成 8 胜 2 负、`p = 0.109`。效应量很大，大概率是真的，但发表出去的显著性
> 超出了单次运行能支撑的范围。

### 6.4 抽取批大小与位置效应

| | |
|---|---|
| **原假设** | 零产出是抽取器的随机波动 |
| **反证（观测）** | 位置 0–3 零产出 6.4%，位置 4–14 是 18.3%，$RR=2.86$，组内置换 $p=0.00005$ |
| **随机对照** | 60 个会话（30 个生产零产出 + 30 个正常，按轮次数 ±2 和助手占比 ±0.08 配对），批大小固定 15，两组随机排列各配一个自己的逆序 |

配对结果（51 个会话同时见过首尾）：

| | 覆盖率视角 | 数量视角 |
|---|---|---|
| 前面出记忆、后面零产出 | **8** | 每会话记忆数，前 **4.5** |
| 后面出记忆、前面零产出 | **0** | 每会话记忆数，后 **1.6** |
| 精确 McNemar | **p = 0.0078** | **p < 0.0001** |

批大小本身：

| 批大小 | 零产出率 | 每会话记忆数 | 全语料抽取请求 |
|---|---:|---:|---:|
| **15（生产）** | 11.7% | **2.7** | 400 |
| 5 | 8.3% | 4.8 | 1,000 |
| 1 | **0.0%** | **12.7** | 4,800 |

60 个会话里**没有一个**在更大批次下产出更多，两次比较都是（p = 1.7e-18）。

**解读**：零产出不是独立的失败模式，是一条连续衰减曲线的尾巴。**机制未定**——输出预算耗尽、
枚举漂移、输入位置效应、schema 长度压力都与数据相符，本实验一个都没分离。

**决定：暂不改。**改了要重建所有 store（免费额度下多 28 个配额日）。写成 v2 的已知天花板，
列为 v3 题目（§8.3）。

**原计划的补救措施是错的**：本来要"把零产出会话捞出来重跑看恢复率"。这个设计会给出一个自信
的错误答案——把它们单独拿出来重新组批等于把它们全挪到了**前面**，恢复率当然高，结论会写成
"随机丢失，加个重试就行"，而真实机制是"我们改变了它们的位置"。更根本的是，重试治的是错的
东西：一个本该产出十条、实际产出两条的会话永远触发不了重试，而按上表那才是损失的大头。

**完整 train150 上的最终零产出审计**（7,180 个会话，1,253 个零产出，267 个低于最低轮数，
986 个进入详细分析）：

| 分类 | 数量 | 能得出什么 |
|---|---:|---|
| 内容审查拒绝 | **0** | — |
| **完全相同输入、不同结果** | **0** | **没有任何直接证据证明模型随机** |
| 源数据格式问题 | 5 | 日期/角色/空文本检查发现 |
| 正确答案证据被漏提取 | 13 | 标注证明这里确实有该保留的信息 |
| 相同文字、不同日期，结果不同 | 175 | 日期也是模型输入，只能算近重复 |
| 短会话，可能本就没有持久信息 | 198 | 合理候选，不冒充已证明 |
| **仍无法确定** | **862** | **保持未知，不用猜测填补** |

### 6.5 检索实验

**交叉编码器重排。** k=10 时重排臂和普通臂对 31 道题给出**完全相同的答案**（零处分歧），
同时在**每个** k 上都**降低**来源召回（k=20 时 93.5% → 90.3%）。它不改变答案，而且在删正确
证据。**不采用**，移入可选 `rerank` extra，torch 移出默认依赖。

**只砍 top_k。** `flatN`（条数减到与 coherent 相同，仍按分数打散）在其中一题上 **1/3** 而
`flat20` 是 **3/3**——**更差**，上下文只有三分之一。变量不是数量，是形状。这个便宜假设先测
再排除，省下了直接去建复杂方案的风险。

**原文回退用 BM25 还是稠密检索。** 一组构造查询显示 BM25 的 R@1 只有 **6.9%**。
**人工检查那些构造查询**，发现构造过程把**问题本身**删掉了——"How long have I been collecting
vintage cameras?" 变成了 `"long"`。证据作废；手写改述能把 gold 轮次检索到**第 1 位**，包括
不含任何源文本特有名词的表述。稠密检索**推迟，不是否决**，并写下了会重启它的条件
（≥50 个已验证的可检索案例且 Recall@3 有明确增益）。

**检索权重（2026-08-25，train150 离线，零配额）。** 七个配置：

| 权重 | Top-3 (mean) | 装配后 | 中位 token | vs 基线 |
|---|---:|---:|---:|---:|
| **仅 semantic 1.0（线上）** | **95.3%** | **95.3%** | 140.5 | — |
| + recency 0.3 | 95.3% | 95.3% | 140.5 | **逐位相同** |
| + importance 0.3 | 90.0% | 90.0% | 134.0 | −5.3 |
| + bm25 0.5 | 89.3% | 89.3% | 138.5 | −6.0 |
| 五路全开 | 87.3% | 87.3% | 151.0 | −8.0 |
| + bm25 1.0 | 86.7% | 86.7% | 136.0 | −8.6 |
| + entity 0.5 | 78.0% | 78.0% | 153.0 | **−17.3** |

**每加一路都掉分。**recency 那一行逐位相同不是巧合——这一路信号在这个语料上恒等于零：

```
记忆年龄     最小 932 天   中位 1,189 天   最大 1,727 天
recency 值   最小 4.7e-18  中位 1.2e-12    最大 4.5e-10
recency > 0.01 的记忆数：0 / 18,519
```

半衰期 30 天，而最"新"的记忆也有 932 天，$2^{-932/30}\approx10^{-10}$。**这是配置缺陷不是
信号缺陷**，也意味着 `recency` 从未真正参与过本项目的任何一次检索（权重本来就是 0，没有造成
错误结论）。其余四路是真的有害：min-max 把弱信号拉到满量程去重排一个本来正确的语义排序；
entity 最差，因为它是"任一实体完全命中即满分"的粗粒度 max。

**决定：保持 semantic-only，此问题关闭。**它**不**证明调过参的混合不可行——没有做权重网格、
没有交互搜索、端点是代理指标而非准确率。它证明的是这四路不是摆在桌上的免费收益。
详见 [`results/retrieval-weights.md`](../results/retrieval-weights.md)。

### 6.6 上下文组装

**五题探针（每题每臂 3 次，共 45 次回答）：**

| 臂 | 上下文 | 三次运行一致的单元格 |
|---|---|---:|
| `flat20` | 生产配置，top_k=20，按分数排 | 3 / 5 |
| `flatN` | 条数与 coherent 相同，仍按分数打散 | 3 / 5 |
| **`coherent`** | gold 会话的记忆，按事件顺序 | **5 / 5** |

`coherent` 买到的主要不是准确率，是**一致性**——它从没跟自己不一致过。两个限制让这还不能算
产品结论：`coherent` 是 oracle（用了 gold session id），而且五道因为答错才被挑出来的题不是
一个样本。

**train150 上的七组固定网格**（完整 150 题，网格在剩余问题到达之前就固定）：

| 配置 | 聚合 | 半径 | 上限 | Top-3 | 装配后 | 中位 token | 被截断 |
|---|---|---:|---:|---:|---:|---:|---:|
| max-whole-cap20 | max | — | 20 | 94.7% | 91.3% | 177.0 | 20 |
| mean-whole-cap20 | mean | — | 20 | 95.3% | 93.3% | 153.0 | 12 |
| mean-r1-cap20 | mean | 1 | 20 | 95.3% | 93.3% | 140.0 | 8 |
| **mean-r1-cap30** | **mean** | **1** | **30** | **95.3%** | **95.3%** | **140.5** | **1** |
| mean-r1-cap40 | mean | 1 | 40 | 95.3% | 95.3% | 140.5 | 0 |
| mean-r2-cap30 | mean | 2 | 30 | 95.3% | 95.3% | 151.5 | 1 |
| max-r1-cap30 | max | 1 | 30 | 94.7% | 94.7% | 157.5 | 3 |

三道门全过：Top-3 95.3% ≥ 80%、装配后 95.3% ≥ 80%、上下文 140.5 / 354.5 = **0.40×** 远低于
1.5× 上限。**选择完全由预先写死的规则决定**：cap30、cap40、r2-cap30 三者在 95.3/95.3 上并列
→「更小的硬上限」淘汰 cap40 →「更小的窗口半径」淘汰 r2 → **mean-r1-cap30**。

值得注意：`mean-r1-cap40` 的被截断数是 **0**，比选中的还好看，肉眼挑大概率会挑它。
规则选了 cap30，因为规则在看到数据之前就写了「更小的上限优先」。**这是预注册在一个小到足以
诱人的决定上真的起了作用。**

按聚合方式看会话召回：

| 聚合 | @1 | @2 | @3 | @5 | 装配后 |
|---|---:|---:|---:|---:|---:|
| max | 86.7% | 91.3% | 94.7% | 97.3% | 94.7% |
| **mean** | 84.7% | 93.3% | **95.3%** | 96.0% | **95.3%** |
| sum_top3 | 50.0% | 66.0% | 75.3% | 88.7% | **74.7%** |
| sum | 42.7% | 65.3% | 75.3% | 88.7% | 74.7% |

`sum_top3` 是配置文件里原本的**起点值**，它的装配后召回 74.7% **低于 80% 的门槛**——
直接把起点当结论发出去会过不了自己注册的门。天花板是 **98.0%**（147/150 题的 gold 会话至少
出现在 top-20 记忆输入里），上下文组装拿到其中 95.3%，中位排名 **1**。

**v2 尚未验证。** 预注册的决策规则明确：`coherent-auto` 只要**不降低**准确率且上下文不超过
+50% 就采纳，**不要求它涨分**——赌的是一致性。**v2 是否提高准确率，在 dev100 跑完之前未知。**

### 6.7 失败分析

**dev50 的 14 个失败，按丢失答案的那一层归类：**

| 阶段 | n | 含义 |
|---|---:|---|
| S0 来源 | 0 | 事实压根不在对话里 |
| **S1 抽取** | **10** | 它从来没变成一条记忆 |
| S2 生命周期 | 1 | 变成了记忆，然后被合并或覆盖掉了 |
| S3 资格 | 0 | 排序之前被过滤掉了 |
| **S4 检索** | **0** | 有资格，但没进上下文 |
| S4b 组装 | 1 | 进了上下文而且排最前，仍没被用上 |
| S5 推理 | 2 | 全部供上且正确，答案还是错 |

**十四个里十个死在抽取，检索一个都没有。**

**模块 oracle 上限——在建之前先量它最多能修好几道题：**

| 模块 | 上限 | 实测 |
|---|---:|---|
| 抽取 | 10 | 试了 9 道，**修好 4 道** |
| **检索** | **0** | **没跑**——没有失败死在这里 |
| 组装 | 1 | 4 次运行里 3 次修好 |
| 推理 | 2 | 0 |

抽取的 oracle 只修好 9 道里的 4 道，这是更有用的那一半：**丢事实之外还有第二个缺陷**，
所以光把抽取做到完美也到不了上限。

**这套分析决定了工程优先级。**检索侧改进的天花板是 0 道题，而抽取有 10 道、推理有 2 道。
这解释了为什么本项目拒绝一个已实现好的重排器、在 BM25 的负面证据上先做人工审计、
把力气放在抽取 schema 和 prompt 上，以及为什么 v2 选的是**上下文组装**而不是继续调检索。

#### 检索成功但答案仍然错

已经确认：检索成功了，证据进了上下文，答案仍然错。`knowledge-update` 那五个失败全部召回了
gold session **和** gold evidence。至少要区分五种原因，负责模块完全不同：

| # | 类别 | 具体样子 | 归谁 |
|---|---|---|---|
| 1 | 上下文组装失败 | 两个日期分别排第 1 和第 2，模型读成了同一天 | 组装 |
| 2 | 时序推理失败 | "我收到吊灯是几周前？"——需要日期算术 | 推理层 |
| 3 | 多会话聚合失败 | "我二月去了几个博物馆？"——没有任何一轮说了这个数 | 查询分解 |
| 4 | 知识更新解读失败 | 拿到新旧两条事实，没能判断哪条现在成立 | 更新语义 |
| 5 | 随机生成 | 同样输入，三次运行里有一次不一样 | 采样 |

**第 5 类被单独量化过**：6/100 翻转，正确率极差 3 点。而且噪声不是弥散的——**六类题里四类
三次运行逐位一致**，所有不一致的题都是 `temporal-reasoning` 或 `multi-session`，即第 2、3 类。
**查找是确定性的；算术和聚合才是采样显形的地方。**

**分题型的泛化情况**（dev50 → heldout100，Fisher 精确检验）：

| 题型 | dev50 | heldout100 | Fisher p |
|---|---:|---:|---:|
| knowledge-update | 8/8 = 100% | **10/15 = 66.7%** | 0.122 |
| single-session-user | 7/7 = 100% | 12/14 = 85.7% | 0.533 |
| single-session-assistant | 6/6 = 100% | 9/11 = 81.8% | 0.515 |
| multi-session | 7/13 = 53.8% | 19/27 = 70.4% | 0.480 |
| single-session-preference | 2/3 = 66.7% | 4/6 = 66.7% | 1.000 |
| **temporal-reasoning** | 6/13 = 46.2% | **16/27 = 59.3%** | 0.509 |

每个 dev50 格子只有 3–13 题。三个 100% 的类别全部下跌、两个最差的全部上升、没有一处能与噪声
区分——**dev50 的分题型数字从来没有携带过信息**，而在它们被用来决定该建什么的时候，
没有人把这句话说出口。

**已经做了的修复**：回答 prompt 重写（区分"从没被提过"和"上下文里有料可用"——修复前电池那题
系统检索对了却拒答）、scope 分组、判分器按题型路由（偏好类 gold 是评分标准不是参考答案）、
会话连贯上下文、重复运行评测。未来方向见 §8.3。

## 7. 工程与可复现性

这些机制共同回答一个问题：**怎么保证一个数字是它声称的那个系统产生的。**

| 机制 | 解决什么 | 实现 |
|---|---|---|
| **摄入指纹** | 续跑时代码已经变了 | 从 Stage A/B 的 prompt 原文、`schema.sql`、模型 id、每请求会话数、去重阈值算哈希；不一致时报出**哪个部件动了** |
| **结果版本化** | 一行结果不知道是哪个系统产生的 | 每行评测记录带回答 prompt、判分 prompt、抽取器版本——**抽取器版本取自 store 而非代码检出**，因为它描述的是被评测的数据 |
| **冻结清单** | "n=50" 不是一个实验身份 | 报告的运行必须指名一个冻结的问题清单；`--limit` 只用于探索 |
| **内容寻址冻结** | 事后偷偷改配置 | 把代码、配置、数据、预注册规则一起哈希；摄入后的冻结只有在这些哈希全部没变时才被接受。名字以 `_for_reference_only` 结尾的字段只记录不比较 |
| **一次性 ledger** | 最终测试被跑第二次 | 状态变 `complete` 后运行器拒绝再执行 |
| **闸门非零退出** | 打印"关闭"却退出 0 | 所有闸门关闭时返回非零 |
| **产物新鲜度** | 读到上一次运行的判决 | 按本次运行的开始时间校验 |
| **跨进程锁** | 两个摄入互相覆盖 | `locking.py`，pid 咨询锁 |
| **配额中断安全** | 在途批次被误判成零产出 | 配额/网络失败不给在途批次写终态也不拿它做分析；内容策略拒绝保留原文并写显式终态；有自动化重放测试证明续跑不产生重复 |
| **只读状态检查** | 续跑前不知道 store 是否一致 | `scripts/check_ingest_state.py` 联合校验 checkpoint / 原文归档 / SQLite 完整性 / 记忆数 / 索引 id / 向量行数 / 抽取器指纹 |
| **测试与 CI** | — | **532 个测试**，ubuntu / windows / macos，行覆盖 80%（关键实验路径 88–100%） |
| **结构化日志** | — | 每请求一条 JSON：request id、延迟、配置指纹。**不含记忆内容、不含凭据** |

**这些机制不是预先设计出来的，每一条都来自一次具体的失败**——一个被两代抽取器写过而无人
察觉的 store、一个打印"关闭"却退出 0 的闸门、一条猜原因的报错、两个互相覆盖配额账目的进程。
完整事故记录见**附录 D**。

**三个对外接口共用同一个 service 对象**，所以它们不可能与被测量的行为漂移：

| 接口 | 形态 |
|---|---|
| REST | FastAPI，9 组端点；每次读都要 `user_id`；**跨命名空间读返回 404 而不是 403**——403 会确认这个 id 存在 |
| MCP | `search_memory` / `remember` / `search_conversations` / `get_timeline` / `forget`；每个工具都要显式 `user_id`，没有隐式会话身份 |
| Memory Inspector | 网页，显示每条记忆为什么被选中、跳过、覆盖，URL 可分享；四个 demo 是**录制的真实运行**，带 store 和 prompt 指纹，任一变化就显示 `stale` |

**Docker**：2.95GB，大部分是 PyTorch。默认安装会拉 CUDA wheel（24.4GB 的 GPU 运行时，装在一个
永远见不到 GPU 的容器里），所以 Dockerfile 装 CPU wheel 并删掉孤立的 CUDA 包。镜像不烘焙任何
数据集、模型、凭据或数据库——store 从挂载卷进来。

## 8. 限制与下一步

### 8.1 当前限制

**抽取损失。**批大小 15 每会话产出 2.6 条记忆，批大小 1 是 12.7 条（§6.4，随机对照）。
本项目所有数字都在这个被压低的天花板之下。这是一个已知量，不是未知数。

**谓语归一化与覆盖。**622 个替换信号只换来 42 次覆盖，88% 的信号独占一个键，其中 96% 的
`(user,subject)` 下还有别的谓语（§3.5）。**有证据的机制假设，尚未证明是那些失败的原因。**

**检索成功之后的推理。**S4 检索失败为 0，而 S4b 组装 1 个、S5 推理 2 个；`knowledge-update`
五个失败全部召回了 gold（§6.7）。五类原因各占多少未知。

**最终基线证据缺失。**`full_context` 和 `naive_rag` 从未在保留集上跑过，所以"结构化记忆打平
普通 RAG"在未见数据上没有证据。这是证据链里最大的缺口。

**存储与鉴权仍是原型。**`user_id` 取自请求正文而非可信令牌；删除只是软状态而非真正抹除；
SQLite 单写 + 咨询锁，多进程写入不承诺；备份有文件但没做过恢复演练；免费额度、无可信价目表，
因此不记美元金额；日志脱敏、密钥管理、保存期限、告警与回滚均未定。验收标准写在
[`PRODUCTIZATION_V2_PLAN.md`](PRODUCTIZATION_V2_PLAN.md)。

**其它已记录的限制**：一次 prompt 变更（2026-08-14 重写 `ANSWER_SYSTEM`）破坏了此前所有数字
的可比性，这是有意的取舍并被明确记录；`stores/two-stage-hydrated.db` 混了两代抽取器
（4,843 行修复前 + 2,265 行修复后），在它上面测的结果一律标注为诊断；时序算术未解决且回退
碰不到它——日期必须被计算，不能被查找；`fallback.max_turns` 从未扫过。

### 8.2 v2 评测的剩余部分

**已完成。**train150 全部 7,180 个会话终态、18,519 条记忆、七组固定网格、最终零产出审计，
以及由固定规则选出的 `configs/v2.yaml`（`mean` / 半径 1 / 上限 30）。

**dev100。**第一次摄入跑到 37%（1,789 / 4,791 个会话，408 次抽取调用）后被**丢弃**——
数据本身没问题，断的是血统：pre-ingest 冻结在源码树尚未提交时捕获，而提交那份工作会移动
`git HEAD`，冻结又比较了这个字段。那些调用写作沉没成本，而不是去做一次事后冻结；
强制逻辑本身也修好了（§7）。重新摄入约 1,400 次调用，随后是 **5 臂 × 3 重复**（约 2,050 次
回答调用）：`flat20` / `coherent-auto` / `coherent-oracle` 是决策臂，
`naive_rag` / `memory-only` 是 2026-08-25 补注册的**报告基线**，它们不能移动产品选择。

**test100。**冻结 + 摄入（约 1,400 次）+ **一次性**运行（约 690 次）。跑完实验部分即结束，
并第一次给出"70% 到底比 naive RAG 好不好，在没见过的数据上"的答案。

**最终报告必须写进去的三句话**（现在定，不等看到数字）：本结果建立在批大小 15 的抽取器上，
是一个被压低的天花板；单次运行噪声为 3 个点，任何小于 3 点的臂间差距不作为结论；
`test100` 为一次性运行，无重复、无多数投票，p 值为描述性。

### 8.3 未来工作

**以下全部尚未实现、尚未验证**，不能读成当前系统已有的能力。

| 方向 | 依据 | 为什么现在不做 |
|---|---|---|
| **批大小 1 / 自适应批** | 4.7 倍产出，因果已确立（§6.4） | 要重建所有 store，10 倍配额 |
| **谓语归一化** | 96% 的替换信号被谓语命名冲散（§3.5） | 改了要重新抽取；但**下一步是免费的**——在现有 store 上模拟"词干化合并后有多少孤立信号能与目标重逢" |
| **确定性时序计算器** | S5 里那一类失败需要日期算术 | 需要在 train150 上先定位边界 |
| **按题型路由** | 噪声集中在时序和多会话两类 | 同上 |
| **显式 current/superseded 消解器** | 在进 prompt 之前定下哪条成立，而不是指望模型推断 | 依赖谓语归一化先落地 |
| **结构化证据表** | 把事实以表格而非散文交给模型 | 未验证 |
| **更强回答器** | 对不稳定题型升级模型 | 应在 test100 之后作为独立消融 |
| **`recency` 半衰期** | 30 天对上 932–1,727 天的语料恒为零（§6.5） | 免费可重测，半衰期应在 300–600 天量级 |
| **生产存储** | SQLite 单写（§4.5） | **实验结论固定之后**才碰，否则实验与工程重构混在一起 |

### 8.4 不承诺什么

- 不宣称打赢任何第三方系统。没有在同一协议下跑过别人的系统。
- 不宣称保留集上有基线对比。
- 不宣称单机 SQLite 支持多进程写入。
- 不把"软删除 memory 状态"说成用户数据已彻底删除。
- 不在没做过恢复演练的情况下说备份可靠。
- 不根据免费额度或过期价格猜真实费用。
- 不把仅靠请求正文里的 `user_id` 说成鉴权。
- 不把"架构支持五路信号"说成"五路都在生产中参与排序"。

## 附录 B —— 数学定义

**嵌入**：$\mathbf e = f_\theta(x)\in\mathbb R^{384}$。$\theta$ 是 `all-MiniLM-L6-v2` 的权重，
本项目只推理不训练。

**余弦 / 归一化内积**

$$\cos(\mathbf q, \mathbf m) = \frac{\mathbf q^\top \mathbf m}{\lVert \mathbf q\rVert\,\lVert \mathbf m\rVert}
\;\xrightarrow{\ \lVert\cdot\rVert=1\ }\;\mathbf q^\top \mathbf m$$

$\mathbf q$ 是查询向量，$\mathbf m$ 是记忆 `content` 的向量，$\mathbf q^\top\mathbf m$ 是内积
$\sum_{i=1}^{384}q_im_i$，$\lVert\cdot\rVert$ 是 L2 范数。所有向量在写入和查询时都被归一化
（§4.3 已用代码确认），所以内积直接就是余弦。取值 $[-1,1]$，融合前搬到 $[0,1]$：
$S_{\text{sem}}=\mathrm{clip}_{[0,1]}((\cos+1)/2)$。

**BM25**

$$\mathrm{BM25}(q,d) = \sum_{t \in q} \mathrm{IDF}(t)\cdot \frac{f(t,d)\,(k_1+1)}{f(t,d) + k_1\left(1 - b + b\,\dfrac{|d|}{\overline{dl}}\right)}$$

| 变量 | 含义 | 直觉 |
|---|---|---|
| $t$ | 查询里的一个词元 | 分词后的一个 token |
| $f(t,d)$ | 词频：$t$ 在文档 $d$ 中出现的次数 | 出现越多越相关，边际递减 |
| $\mathrm{IDF}(t)$ | 逆文档频率 | 罕见词更有区分度 |
| $\lvert d\rvert$ | 文档长度（词元数） | — |
| $\overline{dl}$ | 全库平均文档长度 | — |
| $k_1$ | 词频饱和参数 | 越小越快饱和 |
| $b$ | 长度归一化强度 $\in[0,1]$ | $b=1$ 完全按长度惩罚，$b=0$ 不惩罚 |

常用 IDF：$\mathrm{IDF}(t)=\ln\!\left(\frac{N-n_t+0.5}{n_t+0.5}+1\right)$。
本项目调用 FTS5 内置 `bm25()`，其返回值是标准分数的**负数**；$k_1$ 与 $b$ 由 FTS5 内部固定，
**当前材料无法确认其取值**。

**词法归一化**（对本次查询实际观察到的候选做 min-max，`lower_is_better=True`）：

$$S_{\text{lex}} = \frac{\max_j r_j - r_i}{\max_j r_j - \min_j r_j}$$

$r_i$ 是候选 $i$ 的原始 FTS5 分数。当 $\min\approx\max$（只有一个候选或全部同分）时全部返回
1.0，注释写的是"一个没有歧义的命中拿到满分"。

**时近**：$S_{\text{rec}}=\exp\!\left(-\ln 2\cdot\dfrac{\Delta_{\text{days}}}{H}\right)$，
$H=$ `recency_halflife_days` 默认 30 天，$\Delta$ 从 `event_time`（缺失时用 `ingested_at`）
算起。$\Delta=H$ 时恰为 0.5。

**实体重叠**：$S_{\text{ent}}=\max\limits_{e\in E(m)}\dfrac{\lvert T(e)\cap T(q)\rvert}{\lvert T(e)\rvert}$，
$E(m)$ 是记忆关联的实体，$T(\cdot)$ 是分词（`[a-z0-9]+`，长度 > 2）。取最大而非平均。

**加权融合**：$S(m,q)=w_sS_{\text{sem}}+w_lS_{\text{lex}}+w_rS_{\text{rec}}+w_iS_{\text{imp}}+w_eS_{\text{ent}}$，
可选再乘 `strength`（默认关闭）。

**会话聚合**

$$A_{\max}(s)=\max_{m\in M_s}S(m,q)\qquad A_{\text{sum}}(s)=\sum_{m\in M_s}S(m,q)$$
$$A_{\text{mean}}(s)=\frac{1}{\lvert M_s\rvert}\sum_{m\in M_s}S(m,q)\qquad A_{\text{top3}}(s)=\sum_{j=1}^{3}S_{(j)}$$

$M_s$ 是**检索结果中**来自会话 $s$ 的记忆（不是该会话的全部记忆），$S_{(j)}$ 是其中第 $j$ 高的分。

**准确率**：$\text{Accuracy}=\dfrac{\#\{\text{judge 判对的题}\}}{N}$

**来源会话 Recall@k**：$\text{Recall@}k=\dfrac1N\sum_{i=1}^{N}\mathbf 1[g_i\in R_i^{(k)}]$，
$g_i$ 是第 $i$ 题的 gold 会话，$R_i^{(k)}$ 是排名前 $k$ 的会话集合。本项目在多个阶段分别测它
（候选 → 排序后 → 选中 → 装配后），因为一个端到端数字无法定位是哪一段丢的。

**精确 McNemar 检验**。两个系统跑同一批题：

|  | B 对 | B 错 |
|---|---:|---:|
| **A 对** | $a$ | $b$ |
| **A 错** | $c$ | $d$ |

$a$ 和 $d$ 不携带任何关于差异的信息，丢弃。零假设下每个不一致对独立地以 $1/2$ 落入任一格：

$$b \sim \text{Binomial}(b+c,\ 0.5)$$

双侧精确 $p$ 值是该二项分布的双尾概率。**为什么看不一致而不是两个准确率**：两个系统 70% 和
72%，可能是"完全相同的 70 题都对、B 多对 2 题"（强证据），也可能是"A 对的 70 题里 B 错了 15
题、另外又对了 17 题"（几乎没有证据）。只有不一致格能区分。

**Fisher 精确检验**：用于**非配对**的两组比例比较，例如同一题型在 dev50 与 heldout100 上的
正确数。本项目所有 per-type 比较 $p\ge0.12$，即全部不可区分。

**风险比**：$RR=p_{\text{后段位置}}/p_{\text{前段位置}}$，用于零产出分析。观测数据给出
$RR=2.86$，批聚类 bootstrap 95% CI $[2.15,4.35]$，组内位置置换检验 $p=0.00005$（$N=20{,}000$）。
⚠️ 这是**观测性**的：每个会话只坐过一个位置；因果证据来自 §6.4 的随机对照。

```yaml
  # 未覆盖权重 → config.py 默认：semantic 1.0，其余四路 0.0
  # candidate_limit 默认 50，recency_halflife_days 默认 30

  enabled: true
  max_turns: 3
  max_chars: 2400

  max_sessions: 3
  window_radius: 1            # v2：由 §6.6 的固定规则选出
  max_total_memories: 30      # v2
  aggregate: mean             # v2
  session_order: chronological
  include_superseded: false
```

**模型角色为什么必须分开**：判分器不能给写出这段文字的模型打分（D4，且判分器与人工的一致率
是**被测量的**）；免费额度按模型计量（服务端返回 `…PerProjectPerModel-FreeTier`），
三个角色三个模型才有三个独立池子，这是一次大规模摄入不会饿死评测的原因。
规格选择也有实测理由：完整版 flash 每天只有 20 次请求，连一次 50 题运行都不够；
flash-lite 按分钟限流；抽取一次 dev 子集约 610 万 token，需要 250k TPM；判分输入约 200 token，
TPM 无关紧要，而 gemma 的 1,500 次/天正是判分需要的。

## 附录 D —— 工程事故记录

第 7 章那些机制不是预先设计的。每一条都来自下面某一次具体失败。

**一个 store 被两代抽取器写了，而没有任何东西发现得了。** checkpoint 记了九个进度计数器，
**一个抽取器版本都没记**，而 `set_meta("extractor_version", …)` 是每次运行**覆盖写**不是比对。
结果：一个被 pre-P10 抽取器写到 63% 的 store 被 P10 抽取器续跑完成，两次运行都成功、
所有结构性检查全过。两代的 `source_role` 分布是 93.3%/6.7% 对 44.8%/54.4%。
**修复不是加版本号比对**——版本号是手填的，抓不住"prompt 改了个词"这种更常见的漂移。
改成从输入本身算指纹并报出**哪个部件动了**。那个 store 整个重建，旧的保留不动作为诊断记录，
其上的 60.0% 永久标记为"仅诊断，不进任何对比表"。

**闸门打印"关闭"然后退出 0。** 人看着没问题，任何看返回码的自动化都看不见——无人值守的流水线
会直接开进这道闸门本来要拦住的那次运行。现在闸门关闭一律非零退出。

**陈旧产物不长得像错误。** 从 `temporal-gate.json` 读到 `gate_open: true`，并不能证明**这次**
运行的闸门过了——如果闸门在写文件之前就崩了，磁盘上是上一次的判决。现在按本次运行的开始时间
校验新鲜度。

**一条报错猜了一个没验证过的原因。** `2348/2400 sessions — quota probably ran out`：
配额根本没停过。这条报错被**明确撤回**并记在报告里，理由是"一条猜原因的报错比一条只报观测的
报错更有害，因为它会把下一个人带向错误的方向"。同一处的完整性检查还比错了两个数——
语料有 2,400 个会话**条目**但只有 2,348 个不重复 **ID**，因为同一会话会作为多道题的证据。

**两个进程同时摄入，配额账目被覆盖。** 记了 211 次请求，实际打出去约 320 次。store 里没有
任何一处看起来不对——损坏的是**统计**，不是数据。加了 `locking.py` 的跨进程 pid 咨询锁。

**一个指标错了三次，比抽取器错的次数还多。** 保真度指标在抽取器被改对之前自己先错了两次，
第三次在换成带示例的 prompt 那一轮（D28、D30）。指标错了而结论没错是碰运气。

**会话 id 没做用户作用域。** 会话召回算出约 64%，与其它测量都对不上。两个错叠在一起：脚本把
没跑完的题算进了分母；而且拿数据库里**带作用域的内部 id** 直接跟**公开数据集 id** 比较。
修复后是 95%+，那个 64% 被明确作废。历史 store 做了迁移，**没有重新抽取**那 9,588 条记忆
（保留了 SQLite 备份）。

**干净的库一度让 Mayo 案例失败，而显而易见的诊断是错的。** 一次**改善了检索**的重建之后，
Mayo 问题在两个正式臂里都失败了。诱人的解释是级别分支——第一版只要检索返回了任何东西就取
本地轮次，没有任何东西检查这些记忆是不是关于这个问题的。这**是**一个真实缺陷，但**不是这个**。
真正的原因是截断：检索**确实**找到了正确的对话，但 `turns_for_memories` 返回的轮次**按 session
id 排序**，代码取了 `[:max_turns]`，而 gold 轮次在字母序里排第十（共十六条）——保留的三条全部
来自一段关于现场音乐的对话。**召回变好意味着候选变多，候选变多意味着答案被切掉了。**
在更小的混合 store 上同一问题检索不到东西、直接落到档案、从没遇到那个切片，所以这个缺陷长期
没被发现。两个缺陷是同一个疏漏——没有任何东西拿候选去和问题比较——所以对候选排序同时修好了
两个。`single-session-assistant` 从 5/6 变成 **6/6**，该臂从 66.0% 变成 **72.0%**。

**逐键判定把两句都为真的话互相取代。** 早先的消解实现只要"这个键可消解"就把链上每一对连续
记忆都退休。线上观察到："averaging $100 per week on groceries" 被 "spent $75 at Walmart last
Saturday" 退休了，两句都是真的，原因是 `grocery_spending` 这个键上**某第三条**记忆带了替换
信号。Stage B 的判定单独测试误覆盖率是 0%，损失全部在集成层，所以**逐条事实的判定必须被逐条
尊重**（§3.5 第 6 步）。

**冻结把"仅供参考"的字段当成了强制条件。** `git_head_for_reference_only` 被逐叶比较，于是
**任何一次提交**——哪怕只改 `docs/`——都会让 pre-ingest 冻结失效；而一个在未提交的工作树上
捕获的冻结，只有靠永远不提交它所描述的那份工作才能被遵守。这直接导致 37% 的 dev100 被丢弃
（§8.2）。修复：名字以 `_for_reference_only` 结尾的字段只记录、不比较，每个影响结果的文件
仍然逐个哈希。
