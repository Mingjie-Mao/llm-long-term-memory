## 已实现的候选

当前候选：命令行变体 `two_stage_raw_primary_grounded_v2`，回答策略 `grounded_v2`，
提示版本 `memory-grounded-v2`。首轮候选 `grounded_v1` 的默认校验行为和原执行源码
快照仍保留，不能把后来的修复归到首轮。核心代码位于 `runtime/grounded_answering.py`。

| 目标 | 实现 | 能保证与不能保证的内容 |
|---|---|---|
| 找齐证据 | 复用事实扩展检索键、BM25/向量融合、记忆来源锚点；对完整来源编号，记录最终送入模型的 id、日期、文本哈希及预算遗漏 | 可重放实际输入；覆盖率提高不能直接换算成答题正确率 |
| 解释正确时间 | 分开显示聊天日期、事件表达、日期精度、记忆有效期；日期差根据所引用原话由代码计算；月/年按日历周年计算 | 不把聊天日期用作无日期事件的发生时间；模糊日期保留模糊性；事件关联仍需模型正确选择 |
| 选对计算条目 | 每条记录绑定来源、原话、值、单位、事件/实体标识；验证来源、原话、数值及单位；汇总题要求检查全部来源，两个端点的比较题核对所选证据 | 拒绝无来源数值、缺项和单位冲突；身份标识、题目范围与原话语义仍需要模型判断 |

求和、平均、差值、百分比、计数和日期差由代码执行。相同事件的重复提及合并，
相同价格的不同购买保留为不同事件。发生冲突的同一身份记录须先解决冲突。
缺失证据不等于零。金额采用 Decimal，禁止无依据的货币转换。

二次补取原文保留第一轮证据与编号，继续使用相同模型、结构化响应和计算校验，
最多一次追加回答调用。失败不把未经校验的数字包装成已计算结果。
两轮的调用 token 和延迟累计记录，保存选择条目及拒算原因。

产品 `AnswerEngine(answer_policy="grounded_v2", raw_primary_turn_index=...)` 与评测
`MemoryRunner` 调用同一个实现；对齐 top_k、预算及 fallback 设置后，测试验证两者
发出的模型请求完全一致。当前 REST 服务仍使用默认策略；候选未通过完整对照前
不作默认晋级。旧 v1、v2/v4 实验行为和注册文件保持原样。

## 首轮失败与已验证的修复

首轮 v1 九题诊断保存了 5 条判分结果，其中 1 条答对；随后评分服务在两次执行中
分别返回 503、500。状态为 **INCOMPLETE（5/9）**，不能称为九题准确率。
原始行、调用账本及 120 个源码/配置文件的哈希与文本快照保留在
`results/raw/two_stage_raw_primary_grounded.grounded-diagnostic-v1-rep1.*` 和
`results/analysis/grounded-diagnostic-v1.source-snapshot.json`。

两题的模型条目其实已选对，但程序要求它列出其他无关来源，导致误拒算。新 v2
保留引用校验，差值/时长允许只审阅端点来源；求和/计数/平均仍检查整组来源。
根据未改动的首轮条目，重新从数据库取回原文并验证文本、上下文哈希后，零调用
重放现在可得 `$50` 与 `3 weeks`。另一道事件匹配题仍 scope_incomplete，未解决。
这验证的是计算程序修复，不是新模型答题结果，也不证明整体正确率提升。

生成器 `tools/grounded_operand_replay.py`；结果
`results/analysis/grounded-operand-replay-v2.{json,md}`。

v2 九题外部调用在启动前被自动审批拒绝：审批认为向外部回答/评分服务发送题目和
对话证据需要明确授权。这次执行没有发出 provider 请求，也没有创建 v2 执行账本。
代码、离线回放、完整测试均已完成；模型实测等待这个具体动作的授权。
完整 dev100 六组对照未执行，候选尚未晋级默认服务。
